## 1. 이 절이 증명해야 하는 것

3.1절에서 여섯 계층으로 나눈 구조가 **실제로 확장에 유효한가**를 보이는 절이다. 방법은 기능을 하나 더 붙여 보고 그때 수정된 파일과 줄 수를 제시하는 것이다. 데이터만 추가해서 끝나면 그 계층은 확장에 열려 있는 것이고, 기존 코드를 고쳐야 하면 그 지점이 곧 5.2절의 한계가 된다.

교수님 지시사항: **3.1절의 시스템 구조도를 4.3.1에서 다시 쓰고, 어느 계층이 바뀌었는지 표시해 그 그림을 기반으로 설명할 것.**

## 3. 실험 항목

시간이 부족하면 **A와 C만으로도 절이 성립합니다.** A는 상태머신 계층, C는 월드 오브젝트·데이터 계층을 각각 검증합니다.

### A. 플레이어 상태 1종 추가 — `Consume` (소비 상태)

코드를 확인한 결과, **수정 지점이 네 곳으로 확정**됩니다.

**새로 만드는 것**

- `Assets/Script/State/PlayerState/ActiveState/Consume.cs` — `PlayerState` 상속, 생성자 `(PlayerStateMachine)`
- 소비 애니메이션 클립 1개 + 종료 시점 `OnAnimationFinished` 이벤트 (표 10의 회피와 동일 구성)
- Animator에 `consume` 상태 추가

**기존 코드에서 고쳐야 하는 곳** — 이것이 측정 대상

| 파일 | 위치 | 내용 | 예상 |
|---|---|---|---|
| `PlayerStateMachine.cs` | 11번째 줄 | `enum StateType`에 `Consume` 추가 | 1줄 |
| `PlayerStateMachine.cs` | 61~83번째 줄 | 애니메이션 해시 필드 블록에 `public readonly int consume = Animator.StringToHash("consume");` 추가 | 1줄 |
| `PlayerStateMachine.cs` | `BufferState()` (344번째 줄~) | `case StateType.Consume:` 추가 | 2~3줄 |
| `Inventory.cs` | `UseItem()` | 소비 시 상태 전이 호출 삽입 | 1~2줄 |

애니메이션 해시가 `PlayerStateMachine`의 `readonly int` 필드로 관리되고 있어서, 새 애니메이션을 쓰는 상태는 반드시 이 클래스를 건드려야 합니다. **이것도 개방-폐쇄가 깨지는 지점이라 5.2절에 함께 쓸 재료입니다.**

**고치지 않아도 되는 곳** — 이것이 구조의 성과

- `stateInit()`의 리플렉션 수집부. `PlayerState`를 상속한 비추상 클래스면 자동으로 `Statecaches`에 등록됩니다.
- **입력 등록부 전체.** 퀵슬롯 키는 `QuickSlotUI.Update()`가 `Keyboard.current`로 직접 읽어 `Inventory.UseQuickSlot` → `UseItem`으로 흐르고, 우클릭 메뉴(`ContextMenuUI.Use()`)도 같은 `Inventory.UseItem`으로 들어옵니다. **아이템 사용의 진입점이 `UseItem` 하나뿐이라 상태 전이 삽입도 한 곳이면 두 경로가 모두 처리됩니다.**
- **피격 중단 처리.** `State.isBlock`의 기본값이 `false`라 `OnHit`가 자동으로 `Hit`로 전이시킵니다. `Consume`에서 `isBlock`을 건드리지 않으면 "소비 중 피격 시 중단"이 공짜로 따라옵니다.
- **소모품 ScriptableObject 다섯 종** (`Food`, `Water`, `HealItem`, `DirtyWater`, `TimedEffectItem`). 전부 `OnUse(PlayerStateMachine)`를 오버라이드해 `player.status`만 건드리고 `true`를 반환합니다. 상태 전이를 `UseItem`에 넣으면 이들은 손댈 필요가 없습니다.

### B. 무기 1종 추가

코드를 확인한 결과 **무기 종류를 분기하는 enum이나 switch가 어디에도 없습니다.** `WeaponStatus`는 순수 데이터 ScriptableObject이고, 결정적으로 **애니메이션까지 `AnimatorOverrideController WeaponAnimations` 필드로 들어 있습니다.** `Weapon.cs`는 `status.attack`, `status.stunStrength`만 읽습니다.

**따라서 코드 수정 0줄이 유력합니다.** 만드는 것은 `WeaponStatus` 에셋 1개, `AnimatorOverrideController` 1개, 무기 프리팹 1개.

**단 하나 확인할 것.** `PlayerStateMachine`의 `attackHashes` 배열이 `attack1`, `attack2`, `attack3` 세 개로 고정되어 있습니다. 콤보 단계가 3인 무기면 문제없지만, 단계 수가 다른 무기를 만들면 이 배열을 고쳐야 합니다. **3단 콤보 무기로 실험하면 0줄이 나오고, 일부러 2단짜리로 하면 이 제약이 드러납니다.** 어느 쪽을 보일지 정하고 시작하세요. 개인적으로는 3단으로 0줄을 보이고, 이 제약을 본문에서 한 문장 언급하는 쪽을 권합니다.

### C. 구역 1개 추가 + 블록에이드 해제

코드를 확인한 결과 **구역 식별자(enum, ID, 이름 상수)가 코드베이스 어디에도 없습니다.** 구역은 씬 배치와 `Transform[]` 배열로만 표현됩니다.

- `Blockade`는 완전히 데이터 주도입니다. `keyItem`(ItemBase SO), 두 개의 메시지 문자열이 `SerializeField`이고, 해제는 `keyItem`을 소비한 뒤 `gameObject.SetActive(false)` 한 줄입니다. `BlockadeInteract()`가 `virtual`이라 다르게 동작하는 장애물은 상속으로 만들 수 있습니다.
- `CycleManager`의 `playerBasePosition`, `activeExit`, `exitSpawnPoints`가 전부 `SerializeField`입니다.
- `BaseDepartureGate`의 `explorationStartPoints`도 `Transform[]`입니다.

**따라서 구역 추가도 코드 수정 0줄이 유력합니다.** 만드는 것은 맵 배치, 블록에이드 프리팹 1개, 열쇠 `ItemBase` SO 1개, 그리고 Inspector에서 Transform 배열에 지점 추가.

**다만 진짜 문제가 하나 보입니다.** `CycleManager.RelocateExitFarthestFrom()`이 **전체 `exitSpawnPoints` 중 시작 지점에서 가장 먼 곳**을 고릅니다. 구역이 둘 이상이 되면 아직 열지 않은 구역에 비상구가 배치될 수 있습니다. 구역별로 후보를 나누거나 개방 여부를 확인하는 로직이 필요해집니다. **이게 나오면 4.3.1의 가장 값진 결과입니다.** "데이터만으로 확장되지만 사이클 규칙은 단일 구역을 전제로 작성되어 있었다"는 구체적인 발견이고, 그대로 5.2절로 넘어갑니다.

**그리고 확인해 주셔야 할 것이 있습니다.** 3.6절에 "보스 처치 아이템 기반 영구 개방 및 **기지 빠른 이동** 연동"이라고 적혀 있는데, 저장소 전체를 훑어도 **빠른 이동에 해당하는 코드를 찾지 못했습니다.** `Doorcs`는 단순 여닫이 문이고, `StairObject`는 계단 이동입니다. 구현이 안 되어 있다면 3.6절 서술을 고쳐야 하고, 제가 못 찾은 것이라면 어디 있는지 알려 주세요.

## 4. 커밋 규칙

**실험 하나당 커밋 하나.** 이것이 증거 수집 방식입니다.

1. 실험 시작 전 `git status`가 깨끗한지 확인
2. 해당 확장에 필요한 변경만 수행
3. 커밋
4. `git show --stat HEAD` 출력을 보관

```
git show --stat HEAD
```

커밋 메시지 예시

```
feat: Consume 상태 추가 (4.3.1 확장성 검증 A)
feat: 무기 1종 추가 (4.3.1 확장성 검증 B)
feat: 2구역 및 블록에이드 추가 (4.3.1 확장성 검증 C)
```

**섞지 말 것.** 오타 수정, 로그 제거, 리팩터링을 실험 커밋에 넣으면 줄 수가 오염되어 표를 못 씁니다.
