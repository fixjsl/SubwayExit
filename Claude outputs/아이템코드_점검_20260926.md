## 1. 아이템 코드를 정하는 곳

`ItemBase.itemcode` — 각 아이템 에셋의 인스펙터 필드입니다. `PerkBase`에는 코드가 필요 없습니다. 퍽이 드는 것은 `threshold` 숫자 하나뿐이고, 코드는 `AddGather(item)`가 받은 `ItemBase`에서 읽습니다.

```csharp
public void AddGather(ItemBase item)
{
    if (item != null) gatheredCodes.Add(item.itemcode);   // 코드는 에셋에 이미 있다
}
```

코드를 쓰는 곳은 이미 네 군데입니다.

| 쓰는 곳 | 용도 |
|---|---|
| `Inventory.slots` | `Dictionary<int, int>`의 키 |
| `Inventory.QuickSlots` | `int[2]`, **0을 "빈 칸" 표식으로 사용** |
| `ItemManager.itemDB` | `Dictionary<int, ItemBase>`, 코드로 에셋 역조회 |
| `LootTable.droppedUniqueItemCodes` | 세션 내 유니크 드롭 기록 |

특정 아이템을 지정하는 퍽(예: "붕대 5개 획득")을 만들 거라면 그때도 코드 숫자를 넣지 말고 `public ItemBase targetItem;`으로 에셋 참조를 들면 됩니다. 인스펙터에서 끌어다 넣는 쪽이 Unity 방식이고, 코드를 바꿔도 안 깨집니다.

## 3. 발견한 문제

### 3.1 코드 36이 중복 — 생고기와 에너지드링크

퍽과 무관하게 지금 당장 게임 버그입니다.

`ItemManager.Awake()`는 `itemDB[item.itemcode] = item;`으로 조용히 덮어씁니다. 배열 순서상 뒤에 있는 것만 살아남고, 앞의 것은 `itemDB`에서 사라집니다.

`Inventory.slots`도 코드를 키로 쓰므로 **두 아이템이 한 슬롯에 합산됩니다.** 생고기 2개와 에너지드링크 1개를 들면 `slots[36] = 3`입니다. 결과로 이런 일이 생깁니다.

- `Campfire.CookMeat()`의 `RemoveItem(rawMeat, 1)`이 에너지드링크를 지울 수 있습니다
- `InventoryUI`가 아이콘과 이름을 `itemDB[36]` 하나로만 표시합니다
- `LoseOnDeath`가 `itemDB[36]`의 `weight`로 무게를 되돌리므로 두 아이템의 무게가 다르면 `currentWeight`가 틀어집니다
- `QuickSlots`도 코드를 담으므로 어느 쪽을 등록해도 같은 칸이 됩니다

둘 중 하나의 코드를 바꾸십시오. 생고기는 34, 에너지드링크는 39처럼 빈 번호가 많습니다. 세이브 데이터가 코드를 저장하지 않으니(저장하는 것은 `unlockedPerkIds`뿐) 바꿔도 부작용은 없습니다.

### 3.2 비상구 열쇠의 `itemType: Material` — 의도된 설정 (정정)

확인 결과 설계 의도입니다. 비상구 열쇠는 사망 시 반드시 소실되어야 하는 아이템이므로 `LoseOnDeath`의 `itemType == ItemType.KeyItem` 예외에 걸리지 않도록 `Material`로 둔 것입니다. 진행용 열쇠인 구역 열쇠(`탈출구 열쇠`, 991)만 `KeyItem`입니다.

루트 테이블에서 확인한 배치도 이와 맞습니다.

| 아이템 | 코드 | itemType | 출처 | 사망 시 |
|---|---:|---|---|---|
| 비상구 열쇠 | 999 | Material | 컨테이너 15종 (전부 `isUnique`) | 전량 소실 |
| 탈출구 열쇠 | 991 | KeyItem | 곰(보스) 드롭 | 보존 |
| DummyKey | 0 | KeyItem | DummyTable | 보존 |

`IsUniqueItem(999)`가 true이므로 `LoseOnDeath`에서 부분 소실이 아니라 전량 소실 경로를 탑니다. 의도대로 동작합니다.

### 3.3.1 유니크 기록이 세션 단위여서 비상구 귀환이 세션당 한 번만 가능함

`LootTable.droppedUniqueItemCodes`가 비워지는 시점은 두 곳뿐입니다.

- `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` — 앱 실행 시 한 번
- `GameStartFlow.Awake()`의 `ResetUniquesForNewSession()` — 게임 씬 진입 시 한 번

즉 **세션 단위**입니다. 반면 `BaseReturnExit.OnInteractInternal()`은 귀환할 때마다 열쇠를 소비합니다.

```csharp
if (keyItem != null && !PlayerStateMachine.Instance.inventory.RemoveItem(keyItem, 1))
{
    RefreshPrompt();
    return;
}
```

두 사실을 합치면 이렇게 됩니다.

1. 1사이클 — 컨테이너를 열자 열쇠가 나옴. `Roll()`이 999를 기록. 획득 후 비상구로 귀환. 열쇠 소비됨
2. `ExecuteCycleReset()`이 `ResetContainers()`로 모든 컨테이너의 `contents`를 버림
3. 2사이클 — 컨테이너를 다시 열면 `Roll()`이 `droppedUniqueItemCodes.Contains(999)`로 걸러냄. **열쇠가 어디에서도 나오지 않음**

**한 세션에 비상구 귀환이 단 한 번만 가능합니다.** 사망으로 열쇠를 잃으면 0번입니다. 논문의 핵심인 익스트랙션 사이클 루프의 반복과 정면으로 어긋나고, 탐색 축(비상구 귀환 횟수)의 임계값을 1보다 크게 잡을 수 없습니다.

**고치는 법.** "런 당 하나"의 런을 세션이 아니라 사이클로 보면 됩니다. `CycleManager.ExecuteCycleReset()`에 한 줄입니다.

```csharp
public void ExecuteCycleReset()
{
    TeleportPlayerToBase();
    RespawnMonsters();
    ResetContainers();
    LootTable.ResetUniquesForCycle();       // ← 추가 (기존 ResetUniquesForNewSession 개명)
    HideAllExits();                         // ← 빠져 있음. 3.3.2 참고
    if (departureGate != null) departureGate.ResetForCycle();
}
```

호출 순서는 이미 맞습니다. `Die.Enter()`가 `LoseOnDeath`를 먼저 부르고, 2초 뒤 `RespawnRoutine()`이 `ExecuteCycleReset()`을 부릅니다. 그래서 소실 판정 시점에는 999가 아직 기록되어 있어 전량 소실이 유지되고, 그 뒤에 기록이 비워져 다음 사이클에 열쇠를 다시 찾을 수 있습니다. 사망 페널티와 사이클 반복이 둘 다 성립합니다.

`GameStartFlow.Awake()`의 호출은 첫 사이클용으로 남겨두어도 무해합니다.

### 3.3.2 `ExecuteCycleReset()`에 `HideAllExits()`가 빠져 있음

`CycleManager`에 `HideAllExits()`는 정의되어 있으나 `ExecuteCycleReset()`에서 부르지 않습니다. `used = true`이므로 상호작용은 되지 않지만, 이전 사이클의 비상구 오브젝트가 그 자리에 계속 보입니다. 다음 출발 시 `PlaceExits()`가 위치를 옮기므로 기능 문제는 아니고 시각적 문제입니다.

### 3.3.3 열어보고 안 가져간 경우 — 이전 보고 정정

"컨테이너를 열어 열쇠를 보고 지나치면 그 세션에 다시 못 얻는다"고 썼으나 부정확했습니다. `ContainerObject.contents`는 `CycleReset()`에서만 버려지므로, **그 사이클 안에서는 열쇠가 그 컨테이너에 그대로 남아 있습니다.** 위치를 기억하면 돌아가서 가져올 수 있습니다. 무게나 슬롯이 꽉 차서 못 집은 경우에도 비우고 다시 오면 됩니다.

사이클이 넘어가면 `contents`가 버려지는데, 3.3.1의 수정을 적용하면 그 시점에 유니크 기록도 함께 비워지므로 다음 사이클에 다시 나옵니다. 별도 처리가 필요하지 않습니다.

### 3.4 코드 0이 퀵슬롯에 들어갈 수 없음

`Inventory.QuickSlots`는 `0`을 빈 칸 표식으로 씁니다.

```csharp
if (code == 0 || !slots.ContainsKey(code)) { QuickSlots[slotIndex] = 0; return; }
```

`DummyKey`가 코드 0입니다. 더미라 문제는 없지만, 앞으로 코드 0은 쓰지 마십시오.

### 3.5 더러운 휴지(118)가 고아 에셋

어느 루트 테이블에도 없고 제작 재료로도 쓰이지 않으며 제작 결과물도 아닙니다. 게임 안에서 획득할 방법이 없습니다. 어딘가에 넣거나 지우십시오. 종류 수를 세는 기준이 되므로 남겨두면 분모만 늘립니다.

## 4. 수집 축 임계값의 근거

루트 테이블에서 실제로 나오는 아이템 중 열쇠 2종(991, 999)과 무기를 빼면 **서로 다른 코드 24개**입니다.

```
32, 33, 35, 36, 101, 103, 104, 105, 106, 108, 109, 112,
113, 114, 115, 116, 117, 119, 120, 121, 122, 123, 125, 126
```

코드 36 중복을 고치면 25개가 됩니다.

논문 3.5절에는 이렇게 쓸 수 있습니다.

> 수집 축은 한 세션 동안 획득한 서로 다른 아이템 종류 수를 지표로 삼는다. 탐색으로 획득 가능한 아이템은 24종이며, 임계값은 그중 8종(약 3분의 1)으로 두었다.

총량("50개")으로 쓰지 않는 이유도 함께 서술할 수 있습니다. `ContainerObject.CycleReset()`이 `contents = null`, `hasBeenOpened = false`로 되돌리므로 같은 컨테이너를 사이클마다 다시 수확할 수 있어, 총량 임계값은 시간을 들이면 반드시 충족됩니다. 종류 수는 서로 다른 루트 테이블을 가진 컨테이너를 찾아다녀야 충족되므로 공간 탐색량과 직접 연결됩니다.
