## 1. 남은 코드 작업

### 1.1 `Perks/PerkBase.cs` — `Apply`의 파생값 재계산

**현재 `maxStaminaBonus`와 `carryWeightBonus`가 실제로 반영되지 않습니다.** `Apply`가 원본 필드만 올리고 있습니다.

```csharp
    public void Apply(PlayerStatus status, Inventory inventory)
    {
        status.Maxhp        += maxHpBonus;
        status.MaxStamina   += maxStaminaBonus;
        status.maxCarryWeight += carryWeightBonus;
        if (startingItem != null) inventory.AddItem(startingItem, 1, true);
    }
```

`Inventory.AddItem`이 검사하는 값은 `status.curMaxCarryWeight`인데, 이 값은 `PlayerStatus.Hungry`의 setter에서만 계산됩니다.

```csharp
if (hungry <= 30) curMaxCarryWeight = maxCarryWeight * 0.4f;
else              curMaxCarryWeight = maxCarryWeight;
```

`Stamina`의 setter가 클램프에 쓰는 `curMaxStamina`도 같은 구조로 `Water`의 setter에서만 계산됩니다. 그래서 `maxCarryWeight`와 `MaxStamina`만 올리면 다음 허기·수분 변화가 있을 때까지 상한이 그대로입니다. 허기 배율을 여기서 직접 곱하면 계산 로직이 두 곳으로 갈라지므로, setter를 다시 태우는 쪽이 맞습니다.

```csharp
    public void Apply(PlayerStatus status, Inventory inventory)
    {
        status.Maxhp          += maxHpBonus;
        status.MaxStamina     += maxStaminaBonus;
        status.maxCarryWeight += carryWeightBonus;

        // curMaxStamina와 curMaxCarryWeight는 각 setter에서만 계산되므로 다시 태운다
        status.Water  = status.Water;
        status.Hungry = status.Hungry;

        if (startingItem != null) inventory.AddItem(startingItem, 1, true, false);
    }
```

`status.Water = status.Water;`는 무의미한 대입처럼 보이므로 주석을 반드시 남기십시오. `PlayerStatus`에 `RecalculateDerived()`를 두고 두 setter와 여기서 함께 부르는 편이 깔끔하지만 `PlayerStatus` 수정 범위가 커집니다.

마지막 줄의 네 번째 인수 `false`는 1.2절의 `countAsGathered`입니다. 1.2를 먼저 하시거나 두 파일을 같이 고치십시오.

### 1.2 수집 지표 훅 — `Inventory.AddItem` 한 곳 + 인수 두 곳

**변환 산출물도 셉니다.** 제작·조리·정수로만 얻을 수 있는 아이템이 네 종(붕대, 깨끗한 물, 구운고기, 간이정수기) 있고, 그것들을 얻는 유일한 경로가 변환이므로 세지 않으면 대상으로 쓸 수 없습니다. 특정 아이템 지정 방식에서는 변환을 세도 과대계상이 생기지 않습니다 — 근거는 부록 A에 있습니다.

제외해야 하는 것은 **지급** 둘뿐입니다. `PlayerStateMachine:191`의 시작 지급품과 `PerkBase.Apply:50`의 퍽 시작 아이템입니다. 특히 퍽 아이템을 세면 퍽 A를 골라서 퍽 B를 해금하는 자기참조가 생깁니다.

`Inventory.AddItem`에 플래그를 하나 더 두는 것을 권합니다. 훅이 한 군데로 모이고, 앞으로 획득 경로를 추가할 때 기본값이 "세는 쪽"이라 잊어도 누락되지 않습니다.

```csharp
    public bool AddItem(ItemBase itemBase, int num = 1,
                        bool suppressFirstAcquire = false,
                        bool countAsGathered = true)
    {
        int key = itemBase.itemcode;
        float addWeight = itemBase.weight * num;
        if (currentWeight + addWeight > status.curMaxCarryWeight)
        {
            OnInventoryFull?.Invoke();
            return false;
        }

        if (slots.TryGetValue(key, out int count))
        {
            slots[key] = count + num;
            currentWeight += addWeight;
            if (countAsGathered)
                MetaProgressManager.Instance?.AddGather(itemBase, num);   // ← 추가
            OnInventoryChanged?.Invoke();
            return true;
        }
        if (slots.Count >= (int)status.maxSlots)
        {
            OnSlotsFull?.Invoke();
            return false;
        }
        slots[key] = num;
        currentWeight += addWeight;
        if (countAsGathered)
            MetaProgressManager.Instance?.AddGather(itemBase, num);       // ← 추가
        if (!suppressFirstAcquire)
        {
            bool isNew = acquiredCodes.Add(key);
            if (isNew && itemBase.firstAcquireImage != null)
                OnFirstAcquire?.Invoke(itemBase);
        }
        OnInventoryChanged?.Invoke();
        return true;
    }
```

**성공 경로가 둘이므로 양쪽에 넣으셔야 합니다.** 무게나 슬롯이 꽉 차서 `false`로 돌아가는 경로에서는 세지 않습니다.

그다음 지급 두 곳에 `false`를 넘깁니다.

`State/PlayerState/PlayerStateMachine.cs:191`

```csharp
inventory.AddItem(startItem, startItemCount,
                  suppressFirstAcquire: true, countAsGathered: false);
```

`Perks/PerkBase.cs`의 `Apply`

```csharp
if (startingItem != null)
    inventory.AddItem(startingItem, 1, true, false);
```

`suppressFirstAcquire`를 그대로 쓰지 않고 플래그를 따로 두는 이유가 있습니다. 지금은 두 값이 정확히 겹치지만(지급 두 곳만 `true`), `suppressFirstAcquire`는 "최초 획득 연출을 띄우지 말라"는 연출 지시이고 `countAsGathered`는 "플레이어가 얻어낸 것으로 셀지"라는 진행 판정입니다. 나중에 다른 이유로 연출만 끄고 싶어지면 지표가 조용히 틀어집니다.

**`Inventory`가 `MetaProgressManager`를 알게 되는 것이 이 방식의 대가입니다.** 호출 지점 다섯 곳에 개별로 붙이면 `Inventory`는 퍽 시스템을 계속 모르는 상태로 남습니다. 대신 앞으로 획득 경로를 추가할 때마다 훅을 기억해야 합니다. 논문 3장의 계층 서술을 엄격하게 지키고 싶으시면 개별 방식을, 누락 위험을 줄이고 싶으시면 위 방식을 쓰십시오. `Inventory`는 이미 `ItemManager`, `LootTable`, `PlayerStatus`를 참조하므로 순수 자료 클래스는 아닙니다.

## 3. `PerkBase` 에셋 만들기

`Assets/Data/Perk/` 폴더를 만들고 `Create > Perk`로 생성하십시오. 현재 `[CreateAssetMenu(fileName = "New Perk", menuName = "Perk")]`이므로 메뉴 최상단에 `Perk`로 나옵니다.

축마다 2개씩 6개 기준의 예시입니다. **임계값은 실제 플레이 측정 후 조정하십시오** (6절 마지막 항목).

| PerkId | 이름 | axis | targetItem | threshold | 효과 |

| 1 | (전투 1) | Combat | — | 10 | maxHpBonus |
| 2 | (전투 2) | Combat | — | 25 | maxStaminaBonus |

`PerkId`는 `progress.json`에 저장되는 키입니다. **한번 정하면 바꾸지 마십시오.** 바꾸면 이미 해금한 플레이어의 저장 파일이 엉킵니다. 0은 피하십시오 — 인스펙터 기본값이 0이라 실수로 겹치기 쉽습니다.

## 4. 씬 작업

### `MetaProgressManager`를 프리팹으로

빈 오브젝트를 두 씬에 각각 만들면 `allPerks` 배열이 두 벌이 되어 퍽을 추가할 때 한쪽만 고치게 됩니다. 프리팹으로 만들어 배열을 한 군데로 모으십시오.

역할은 이렇게 나뉩니다. **메인 메뉴 씬의 것이 실제로 일합니다** — 해금 목록을 조회하고 선택을 `pending`에 담고 `DontDestroyOnLoad`로 게임 씬까지 따라갑니다. **게임 씬의 것은 개발 편의용**이라 정상 흐름에서는 싱글턴 가드가 바로 파괴합니다. 에디터에서 게임 씬만 재생할 때 매니저가 없어 널이 되는 걸 막아줍니다.

### `StartMenuScene`

- `MetaProgressManager` 프리팹 배치, `allPerks`에 퍽 6개 연결
- `PerkSelectUI` — 메인 메뉴 캔버스에. 시작 버튼을 눌렀을 때 뜰 패널
- `panel`, `buttonContainer`, `buttonPrefab`, `confirmButton`, `lockedSprite` 연결

### `Base&Main1`

- `MetaProgressManager` 프리팹 배치
- (1.4를 하면) `GameOverUI`의 `unlockLabel` 연결

### 버튼 프리팹

`PerkButton` 컴포넌트를 붙이고 `button`, `background`, `icon`, `label` 넷을 인스펙터에서 연결하십시오. 레이아웃은 `ZoneSelectUI`의 버튼을 복제해 쓰시면 빠릅니다.

**Project 창의 프리팹 에셋을 연결하십시오.** 씬 오브젝트를 넣으면 `PerkSelectUI.Show()`의 정리 루프가 같이 지워서 `MissingReferenceException`이 납니다. `ZoneSelectUI`에서 겪은 그것입니다.

`label`은 `TMP_Text`입니다. 일반 `Text`를 넣으면 연결이 안 됩니다.

## 5. 정하셔야 할 것

**보스 처치를 전투 축에 셀지.** 현재 `AddKill()`은 `MonsterStates.Die.Enter()`에 있고, `BossStateMachine`은 `OnDieHandler`를 `ChangeState<BossDie>()`로 오버라이드하므로 **보스는 세어지지 않습니다.** 세려면 `BossDie.Enter()`에도 같은 한 줄을 넣으십시오. 보스는 사이클마다 리스폰되지 않아 세션당 최대 1회이므로, 세든 안 세든 임계값에 큰 영향은 없습니다. 안 세는 쪽이 "일반 몬스터 처치 수"로 정의가 깔끔합니다.

| `ItemPickup.OnInteractInternal:20` | 바닥에서 줍기, 몬스터 드롭 | 센다 |

| `PerkBase.Apply:50` | 퍽의 시작 아이템 | **세지 않는다** |

### 변환을 세는 이유

**제작·조리·정수로만 얻을 수 있는 아이템이 있습니다.**

| 코드 | 아이템 | 유일한 획득 경로 |
|---:|---|---|
| 31 | 붕대 | 제작 (헌 천 + 고무조각 + 청테이프) |
| 37 | 깨끗한 물 | 제작 (더러운 물 + 정수기 필터), 간이정수기 |
| 38 | 구운고기 | 캠프파이어 조리 (생고기) |
| 998 | 간이정수기 | 제작 (깨끗한 천 + 자갈 + 조약돌 + 청테이프 + 커다란 생수통 + 1종) |

이 넷은 루트 테이블에 없습니다. 변환을 세지 않으면 `targetItem`으로 지정할 수 없고, 지정하면 영구히 해금되지 않는 퍽이 됩니다.

### 과대계상이 생기지 않는 이유

변환은 인벤토리 순증가량이 0이므로 **총량을 세는 설계에서는** 기지에서 자원을 순환시키는 것만으로 수치가 올랐습니다. 특정 아이템을 지정하는 설계에서는 그 문제가 사라집니다. "붕대 5개 획득"을 채우려면 붕대를 다섯 번 만들어야 하고, 한 번마다 헌 천·고무조각·청테이프를 실제로 모아야 합니다. 공짜가 아닙니다.

무한 루프도 없습니다. 제작 연쇄 중 자기 입력으로 돌아오는 것이 하나도 없습니다.

| 변환 | 소비 | 산출 | 되돌릴 수 있나 |
|---|---|---|---|
| 정수 | 더러운 물 + 정수기 필터 | 깨끗한 물 | 아니오 |
| 조리 | 생고기 | 구운고기 | 아니오 |
| 붕대 제작 | 헌 천 + 고무조각 + 청테이프 | 붕대 | 아니오 |
| 고무호스 제작 | 고무조각 | 고무호스 | 아니오 |
| 간이정수기 제작 | 재료 6종 | 간이정수기 | 아니오 |

모든 변환이 재료를 소비하고 한 방향으로만 흐르므로, 어떤 아이템도 반복으로 무한히 늘릴 수 없습니다.

### 지급을 세지 않는 이유

`PerkBase.Apply`의 시작 아이템을 세면 **퍽 A를 골라서 퍽 B를 해금하는 자기참조**가 생깁니다. 플레이는 하나도 하지 않고 시작 아이템만 받아 게임오버해도 조건이 채워질 수 있습니다.

`PlayerStateMachine`의 시작 지급품은 플레이어가 한 일이 아닙니다.

### 탐색 축은 `BaseReturnExit`에 붙은 것이 맞다

탐색을 `CycleManager.ExecuteCycleReset`에서 세면 **사망도 같은 함수를 부르기 때문에** 실패가 탐색 성과로 잡힙니다. `BaseReturnExit.OnInteractInternal`에 붙어 있는 현재 구현이 맞습니다.

### 논문 3.5절의 수집 축 정의

변환을 포함하므로 "탐색으로 모은 양"이 아니라 **"세션 중 획득한 아이템"**으로 정의하십시오. 다음 정도로 쓰면 됩니다.

> 수집 축은 한 세션 동안 획득한 지정 아이템의 수를 지표로 삼는다. 탐색 중 습득한 것과 제작·조리로 얻은 것을 모두 포함하며, 세션 시작 시 지급되는 아이템은 제외한다.
