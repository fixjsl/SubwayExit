## 완료된 측정의 결과 요약

### M1 — 구간별 기본 성능 ([표 12], [표 13])
기지 / 탐색 구역 / 보스 전투 각 3런. 가장 무거울 것으로 예상했던 보스 전투가 실제로는 가장 가벼웠다(드로우콜 62.7, 삼각형 159,776). 부하를 결정하는 것은 전투 연산이 아니라 공간의 기하 복잡도였으며, 이는 화면 공간 조명이 오브젝트 수가 아닌 해상도에 비례한다는 3.9절 설계와 일관된다. 프레임당 GC는 세 구간 모두 1,300 B 내외로 동일.

### M2 · M6 — 조명 합성 패스 ([표 15])
렌더 스레드의 `FlashlightPass` 마커, 조건당 2,000프레임, Profile Analyzer. 광원 1 / 2 / 4개에서 중앙값 9.0 / 10.4 / 9.3 µs로 단조 증가하지 않았고, 프레임 기여도는 0.86 → 0.84 → 0.83 %로 오히려 감소. **GC 할당은 세 조건 모두 0 B**(총합 포함).

### M3 — SSAO 비교 ([표 16])
조건당 3런, 두 조건의 프레임 시간 범위가 겹치지 않음(1.052~1.067 vs 1.153~1.159). 삼각형이 **정확히 2배** 증가(214,121 → 428,094) — SSAO의 깊이·법선 프리패스가 씬 지오메트리를 한 번 더 렌더링하기 때문. 드로우콜 +44.3%, 프레임 시간 +9.2%. 이것이 SSAO 제거의 근거다.

### M4 — 국소광원 구성 ([표 14])
동일 위치(삼각형 편차 0.13% 이내), SSAO 미적용. 광원을 1개에서 4개로 늘려도 **드로우콜 61, SetPass 39가 기준과 동일**. 프레임 시간 증가분은 모닥불 프리팹의 연출 에셋 몫이며 그중 절반이 파티클.

## M5 — 정적 캐시(`YeildCache`) 적용 / 미적용 비교 〔권장, 미착수〕

### 왜 하는가
3.9절 「CPU 측의 할당 억제」에 이렇게 써 두었다.

> 일정 주기로 동작하는 코루틴에서 반복 사용되는 대기 객체는 간격별로 정적 캐시에 보관하여 재사용한다. 이 캐시를 사용하는 코루틴은 세 곳으로, 플레이어의 소음과 밝기를 산출하는 루틴은 매 프레임, 몬스터의 탐지 판정 루틴은 0.1초 주기, 게임 내 시간을 진행시키는 루틴은 2.5초 주기로 동작한다. **캐시가 없을 경우 각 주기마다 대기 객체가 새로 생성되므로, 특히 매 프레임 동작하는 루틴에서 지속적인 힙 할당이 발생한다.**

본문이 "캐시가 없으면 할당이 발생한다"고 단정하고 있으므로, 그것을 보이는 측정이 있으면 서술이 완결된다.

### 왜 필수가 아닌가
[표 15]가 렌더 패스의 프레임당 할당이 0 B임을 이미 보였고, M1·M4 전반에서 프레임당 GC 기준선이 1,204 B로 일정하게 유지되는 것이 간접 근거가 된다. 다만 이들은 **렌더링 경로**의 근거이고, 정적 캐시는 **게임 로직** 쪽이라 직접 근거는 아직 없다.

### 왜 가치가 있는가
3.9절 스스로 밝혔듯 화면 공간 조명은 게임의 시각적 전제라서 적용/미적용 비교가 성립하지 않는다. **정적 캐시는 진짜 A/B가 가능한 몇 안 되는 항목**이다.

### 방법
1. `Assets/Script/Manager/YeildCache.cs`의 `GetIntervals(t)` 호출부를 `new WaitForSeconds(t)`로 바꾼 임시 빌드를 만든다 (코드 한 줄 수준, 커밋하지 말 것)
2. 동일 위치에서 각 3런
3. 지표는 **프레임당 GC 할당 바이트** 하나면 충분

### 예상 결과
매 프레임 도는 소음·밝기 루틴 때문에 미적용 조건의 프레임당 할당이 기준선보다 뚜렷이 올라갈 것이다. 올라가면 그대로 표 한 줄, 안 올라가면 "측정 범위에서는 유의한 차이가 없었다"로 정직하게 적고 넘어가면 된다.

### 소요
빌드 1회 + 6런, 약 10분.

## M7 — 몬스터 수에 따른 부하 〔선택, 미착수〕

3.3절의 탐지 판정이 몬스터마다 0.1초 주기로 `Physics.OverlapBox`와 `Linecast`를 수행한다. 몬스터 0 / 5 / 10마리 × 3런, 지표는 프레임 시간과 프레임당 GC.

`MonsterStateMachine`의 `Physics.OverlapBox`가 호출마다 `Collider[]`를 새로 할당하므로 GC가 몬스터 수에 비례해 증가할 것으로 예상된다. 그렇게 나오면 5장 한계에 "`NonAlloc` 계열 API를 사용하지 않았다"로 연결한다.

## M8 — 사이클 리셋 순간의 프레임 스파이크 〔선택, 미착수〕

3.5절의 리셋이 몬스터 복원과 컨테이너 복구를 함께 호출하므로 한 프레임에 몰릴 수 있다. 리셋을 포함해 1런, raw CSV의 `frame_ms` 최대값과 그 전후를 본다. 튀지 않으면 "체감 끊김 없이 처리된다", 튀면 5장 한계. 어느 쪽이든 쓸 내용이 나온다.

## 측정 위생 — 오늘 겪은 사고와 예방

오늘 조건이 어긋난 채로 측정한 뒤 나중에 발견해 다시 찍은 일이 네 번 있었다. **런이 끝날 때마다 summary CSV의 네 줄만 확인하면 전부 그 자리에서 잡힌다.**

| 확인할 줄 | 정상값 | 어긋나면 |
|---|---|---|
| 해상도 | `1920x1080` | 창 크기가 바뀐 것 — 실행 인자로 고정 |
| 평균 SetPass 호출 | 39~40 (SSAO 끔) / 50 (SSAO 켬) | 의도하지 않은 빌드 |
| 평균 삼각형 수 | 조건 간 편차 1% 이내 | 측정 위치가 다름 |
| 프레임당 GC 할당 | 1,204 B 부근 | 예외 폭주 가능성 — `Player.log` 확인 |

그 외 빌드 설정: **Script Debugging 해제**, Wait For Managed Debugger 해제, Development Build 유지, Fullscreen Mode = Windowed, PerfLogger `showOverlay = false`.

실행 인자로 해상도를 고정하려면:

```
SubwayExit.exe -screen-width 1920 -screen-height 1080 -screen-fullscreen 0
```

예외 로그 위치: `%USERPROFILE%\AppData\LocalLow\<회사명>\<제품명>\Player.log` (직전 실행분은 `Player-prev.log`)

## 결과 정리 시 주의

- **조건당 3런이 최소선.** 런 간 변동이 약 0.06 ms(3%)로 확인되었으므로 1런으로는 효과와 잡음을 구분할 수 없다.
- **최대 프레임 시간에는 단발 이상치가 섞인다.** 99퍼센타일을 쓰거나, 최대값을 쓰되 이상치임을 각주로 밝힌다. (탐색 구역 1회차 17.6초 지점의 85.5 ms 등)
- **드로우콜이 0으로 찍힌 프레임**은 다음 프레임이 2배값으로 나오는 수집 아티팩트다. 1만 프레임 중 몇 개라 평균에 영향 없음.
- **개발 빌드 한계를 각주로 명시.** "측정은 프로파일러 계측이 활성화된 개발 빌드에서 수행되었으므로, 배포 빌드의 실제 성능은 이보다 높을 것으로 예상된다."
- **프레임 제한 해제도 각주로.** "수직 동기화 해제와 프레임 제한 해제는 프레임 시간을 정확히 측정하기 위한 설정이며, 배포 빌드에서는 수직 동기화를 적용한다."
- **[표 15]는 렌더 스레드의 CPU 시간이며 GPU 실행 시간이 아니다.** 본문에서 "실행 비용"이라고만 쓰면 GPU 시간으로 오해된다.
- **원자료 보관.** 측정 CSV와 프로파일러 스크린샷을 저장소(`Docs/measurements/` 등)에 커밋하고, 표 각주에 "측정 원자료는 프로젝트 저장소에 공개되어 있다"를 한 줄 넣으면 재현성 항목에서 점수가 된다.
