[표 14] 등록 광원 수에 따른 조명 합성 패스와 광원 데이터 갱신의 실행 비용

※ 조명 합성 패스는 렌더 스레드의 FlashlightPass 마커, 광원 데이터 갱신은 메인 스레드의 ScreenPointLightManager.LateUpdate 마커이다. 두 스레드는 병렬로 동작하므로 두 값을 합산할 수 없다. 광원 1개 조건은 상시 배치된 비상구 표지등만 등록된 상태이며, 4개는 동시 처리 상한이다.

※ 프로파일러를 빌드에 연결하여 조건당 2,000프레임을 수집한 뒤 Profile Analyzer의 Total 분석으로 산출하였다. 조명 합성 패스는 카메라마다 1회 실행되어 프레임당 2회 기록되므로(조건별 표본 3,998회) 표의 값은 두 실행을 합한 프레임당 총량이며, 광원 데이터 갱신은 프레임당 1회 실행된다.

※ 각 조건의 최대값은 수천 프레임 중 한두 프레임에서 발생한 단발 이상치가 지배하므로 표에서 제외하였다.

※ 본 측정은 프로파일러 연결 상태에서 수행되었으므로, 이때의 프레임 시간과 FPS는 [표 12]의 값과 직접 비교할 수 없다. 또한 제시한 값은 CPU 시간이며 GPU 실행 시간이 아니다.

조명 합성 패스의 실행 시간은 프레임당 합계 기준 중앙값 9.0~10.4 µs였으며, 전체 프레임 시간에서 차지하는 비중은 0.83~0.86%로 1%를 넘지 않았다. 등록된 광원 수를 1개에서 4개로 늘렸을 때 중앙값은 9.0 → 10.4 → 9.3 µs로 단조 증가하지 않았고, 프레임 기여도는 0.86 → 0.84 → 0.83%로 오히려 감소하였다. 조명 합성이 화면을 덮는 단일 삼각형에 대한 한 차례 연산으로 수행되므로, 등록된 광원의 수가 패스의 비용을 결정하지 않음을 확인할 수 있다.

반면 광원의 월드 좌표를 화면 좌표로 변환하여 셰이더에 전달하는 ScreenPointLightManager의 갱신 루틴은 다른 양상을 보였다. 이 루틴은 렌더 스레드가 아닌 메인 스레드에서 동작하며, 중앙값이 2.6 → 2.9 → 3.8 µs, 프레임 기여도가 0.23 → 0.25 → 0.32%로 등록 광원 수에 따라 단조 증가하였다. 증가분은 광원 1개당 약 0.4 µs로, 이 루틴이 등록된 광원마다 좌표 변환을 한 차례씩 수행하기 때문이다. 즉 광원 수에 비례하는 비용은 화면 공간에서 조명을 합성하는 단계가 아니라 그 입력을 준비하는 CPU 측 단계에 국한되며, 그 절대량 또한 동시 처리 상한인 4개에서 3.8 µs로 프레임 시간의 0.32%에 그친다.

두 루틴 모두 프레임당 가비지 컬렉션 할당량은 세 조건에서 0 B로, 최대값과 총합 또한 0 B였다. 이는 3.9절에서 서술한 프로퍼티 식별자의 정적 캐싱, 광원 배열의 사전 할당, 정적 람다를 통한 클로저 생성 억제가 실제로 프레임당 할당을 발생시키지 않음을 보여준다.
