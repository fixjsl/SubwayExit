# 3.9 렌더링 및 최적화 (v3)

> 본 판본의 모든 문장은 코드·셰이더·에셋에서 직접 확인한 사실만으로 구성하였다.
> 문서 끝의 **근거 대조표**에서 문장별 확인 위치를 확인할 수 있다.

## 본문

본 게임은 폐쇄된 지하철이라는 어두운 공간을 배경으로 하며, 플레이어의 시야는 손전등이 비추는 범위로 제한된다. 이때 조명은 단순한 시각적 연출이 아니라 플레이어가 인지할 수 있는 정보의 범위를 결정하는 게임플레이 요소로 작동한다. El-Nasr 외(2007)는 게임 상태에 따라 실시간으로 변화하는 조명이 플레이어의 정서적 경험에 영향을 미친다고 보고, 영화의 조명 기법에서 도출한 패턴을 실시간으로 적용하는 조명 엔진을 구현하여 그 가능성을 제시하였다. 본 게임 역시 어둠과 빛의 대비를 위협 인지의 핵심 축으로 삼으므로, 조명 시스템은 표현력과 실행 성능을 동시에 만족해야 하는 제약을 가진다.

이러한 요구를 충족하기 위해 본 연구는 유니티의 광원 컴포넌트를 장면에 배치하는 일반적인 방식 대신, URP(Universal Render Pipeline)의 `ScriptableRendererFeature`를 상속한 사용자 정의 렌더 패스를 파이프라인에 삽입하여 화면 공간에서 조명을 계산하는 방식을 채택하였다. 장면에 배치된 광원을 사용하는 포워드 렌더링에서는 광원 하나가 추가될 때마다 그 영향을 받는 오브젝트마다 조명 연산이 누적되는 반면, 화면 공간에서 조명을 처리하면 연산량이 장면의 오브젝트 수가 아니라 화면 해상도에 비례하는 단일 패스로 수렴한다. 기하 정보를 화면 공간 버퍼에 보존한 뒤 그 위의 합성을 후처리 단계로 분리하는 접근은 Saito와 Takahashi(1990)가 G-buffer 개념으로 제시한 이래 널리 쓰이는 구성이며, 본 연구의 조명 패스 또한 이 구성을 따른다.

### 렌더 패스의 구성

구현된 렌더 패스는 RenderGraph API를 사용하며, 모든 불투명 및 투명 오브젝트가 그려진 뒤의 시점에 삽입된다. 스프라이트를 포함한 모든 표현물이 화면에 올라온 뒤에 조명을 합성해야 하기 때문이다.

패스는 두 단계로 동작한다. 먼저 현재 화면을 깊이 버퍼를 갖지 않는 별도의 텍스처로 복사한다. 동일한 텍스처를 읽으면서 동시에 쓸 수 없으므로 원본 스냅샷을 확보하는 것이다. 다음으로 이 스냅샷을 입력으로 받아 조명을 합성한다. 프래그먼트 셰이더는 도형이 그려질 때에만 실행되므로 화면 전체의 픽셀에서 조명을 계산하려면 화면을 덮는 도형이 필요한데, 이는 URP가 제공하는 전체 화면 블릿 구조를 사용하여 별도의 메시 자산 없이 삼각형 하나를 그리는 방식으로 해결하였다. 본 연구가 작성한 것은 그 위에서 실행되는 프래그먼트 셰이더이다.

### 손전등의 원뿔 계산

손전등은 장면에 배치된 스포트라이트가 아니라, 플레이어의 월드 좌표와 조준 방향을 뷰포트 좌표로 변환한 뒤 셰이더에서 해석적으로 계산되는 원뿔 마스크이다. CPU 측에서는 플레이어의 위치와 조준 끝점을 각각 뷰포트 좌표로 변환한 다음 그 차이를 정규화하여 화면 공간상의 2차원 조준 방향을 산출한다. 캐릭터의 3차원 회전과 무관하게 화면 기준의 방향을 얻기 위한 처리이다.

셰이더는 이 정보를 받아 픽셀마다 원뿔 내부 여부를 판정한다. 이때 각 픽셀에 대해 역삼각함수를 호출하여 각도를 구하는 대신, 조준 방향에 대한 전방 성분과 수직 성분의 비율을 내각·외각의 탄젠트 값과 비교하는 방식을 취하였다. 탄젠트 계산은 원뿔의 내각과 외각에 대해 각각 한 번씩만 수행되며, 픽셀 단위 연산은 나눗셈과 비교로 축소된다. 거리에 따른 감쇠는 사거리에 대한 거리의 비율을 1에서 뺀 값을 제곱하여 적용함으로써, 광원 근처에서는 완만하고 사거리 끝에서는 급격히 어두워지도록 하였다. 원뿔의 각도 경계와 사거리 끝단에는 각각 별도의 그라데이션 폭을 두어 경계가 드러나지 않도록 하였다.

또한 플레이어 기준의 바닥과 천장 높이를 뷰포트 Y 좌표로 변환하여 셰이더에 전달하고, 원뿔 내부에서 해당 높이에 근접한 픽셀에 띠 형태의 하이라이트를 추가하였다. 빛이 바닥과 천장에 닿아 반사되는 인상을 만들기 위한 처리로, 두 경계의 Y 좌표와 하이라이트의 두께를 하나의 4차원 벡터에 함께 담아 전달함으로써 셰이더 프로퍼티 설정 횟수를 줄였다.

### 국소 광원의 관리

모닥불과 같은 국소 광원은 전용 매니저가 통합 관리한다. 각 광원은 활성화 시점에 매니저에 등록되고 비활성화 시 해제되며, 매니저는 매 프레임 말미에 등록된 광원의 월드 좌표를 뷰포트 좌표로 변환한 뒤 위치·범위·강도를 하나의 4차원 벡터로 묶어 전역 셰이더 배열에 전달한다. 손전등이 화면 전체를 대상으로 하는 것과 달리 이들 광원은 동일한 패스 안에서 추가로 합성되며, 셰이더는 화면비를 보정한 거리를 기준으로 손전등과 동일한 방식의 감쇠를 계산한 뒤 손전등의 마스크와 합산한다.

동시에 처리 가능한 광원의 수는 4개로 제한하였다. 셰이더의 배열은 고정 크기로 선언되어야 하고 전역 벡터 배열의 크기 또한 최초 설정 시점에 확정되므로 상한을 컴파일 시점에 정해야 하며, 본 게임에서 한 화면에 동시에 존재하는 국소 광원이 그보다 많지 않아 이 값으로 두었다.

### 프래그먼트 단계의 연산 축소

조명 셰이더는 화면의 모든 픽셀에서 실행되므로, 불필요한 연산을 프래그먼트 단계에 진입하기 전에 차단하는 것이 비용 절감에 직접적으로 작용한다. 본 연구는 두 가지 처리를 적용하였다.

첫째, 플레이 영역의 상하 경계를 벗어난 픽셀은 조명 계산에 진입하기 전에 어둡게 처리한 색을 곧바로 반환하도록 하였다. 본 게임은 2.5차원 횡스크롤 구성이므로 화면의 상단과 하단 상당 부분이 플레이 영역 바깥에 해당하며, 해당 구간에서는 원뿔 판정과 광원 반복이 모두 생략된다.

둘째, 국소 광원을 순회하는 반복문이 배열의 고정 크기가 아니라 실제 등록된 광원 수만큼만 돌도록 하였다. 화면에 광원이 하나도 없는 경우 반복문 자체가 수행되지 않는다.

### CPU 측의 할당 억제

렌더 패스는 매 프레임 실행되므로, 프레임마다 반복되는 힙 할당을 억제하는 데 중점을 두었다. 렌더 패스가 셰이더에 값을 전달할 때 사용하는 프로퍼티 참조는 문자열로부터 얻은 식별자를 정적 정수 상수로 캐싱하여, 매 프레임 발생하는 문자열 해싱을 제거하였다. 광원 데이터 전달에 사용되는 배열은 고정 크기로 사전 할당하여 재사용하며, 렌더 패스의 실행 함수 또한 정적 람다로 작성하여 외부 변수를 포획하는 클로저 객체가 프레임마다 생성되지 않도록 하였다.

같은 원칙이 게임 로직에도 적용되었다. 일정 주기로 동작하는 코루틴에서 반복 사용되는 대기 객체는 간격별로 정적 캐시에 보관하여 재사용한다. 이 캐시를 사용하는 코루틴은 세 곳으로, 플레이어의 소음과 밝기를 산출하는 루틴은 매 프레임, 몬스터의 탐지 판정 루틴은 0.1초 주기, 게임 내 시간을 진행시키는 루틴은 2.5초 주기로 동작한다. 캐시가 없을 경우 각 주기마다 대기 객체가 새로 생성되므로, 특히 매 프레임 동작하는 루틴에서 지속적인 힙 할당이 발생한다.

한편 물리 질의에 사용되는 레이어 인덱스 또한 정적 클래스에 한 차례만 조회하여 보관하였다. 다만 이 조회는 상태 전이나 상호작용처럼 이벤트 시점에만 발생하므로 연산량 측면의 이득은 크지 않으며, 레이어 이름을 문자열로 반복 기술할 때 발생할 수 있는 오기입을 배제하는 것이 주된 목적이다.

### 실행 환경

성능 측정의 재현을 위해 본 게임이 사용하는 파이프라인 구성을 [표 N]에 정리한다. 본 프로젝트는 유니티 6의 Universal 3D 템플릿에서 시작하였으므로, 표에 제시한 값의 대부분은 템플릿이 제공하는 기본 구성을 그대로 사용한 것이다. 본 연구가 이 계층에서 추가한 것은 앞서 서술한 사용자 정의 조명 패스를 렌더러에 등록한 것이다. 템플릿은 PC와 모바일 두 개의 품질 프로파일을 함께 제공하나, 본 게임은 PC를 대상으로 하며 모바일 프로파일의 렌더러에는 조명 패스가 등록되어 있지 않으므로 사용하지 않는다.

한편 설계 단계에서는 조명 패스와 함께 URP가 제공하는 화면 공간 앰비언트 오클루전(SSAO)을 적용하였으나, 이후 측정 과정에서 제거하였다. 그 경위는 4장에서 다룬다.

**[표 N] 본 게임의 렌더 파이프라인 구성**

| 항목 | 설정값 | 비고 |
|---|---|---|
| 렌더 파이프라인 에셋 | PC 프로파일 | 템플릿 기본 |
| 사용자 정의 렌더러 피처 | 화면 공간 조명 합성 패스 | **본 연구에서 추가** |
| SRP Batcher | 활성화 | 템플릿 기본 |
| Dynamic Batching | 비활성화 | 템플릿 기본 |
| 렌더 스케일 | 1.0 | 템플릿 기본 |
| 그림자 거리 | 50 | 템플릿 기본 |
| 그림자 캐스케이드 | 4 | 템플릿 기본 |
| MSAA | 비활성화 | 템플릿 기본 |
| LOD Cross Fade | 활성화 | 템플릿 기본 |
| SSAO | 미사용 | 설계 단계에서 적용 후 제거 (4장) |

### 검증의 범위

본 절에서 서술한 내용은 설계 단계에서 적용한 기법들이며, 이들이 실제 실행 환경에서 어떤 비용을 갖는지는 4장에서 측정한다.

다만 측정의 범위에는 제약이 있다. 화면 공간 조명은 본 게임의 시각적 전제 자체를 구성하므로, 이를 적용하지 않은 상태는 동일한 게임이 아니며 따라서 적용 여부에 따른 비교가 성립하지 않는다. 이에 4장에서는 조명 패스의 실행 비용을 직접 측정하고, 설계 단계에서 함께 적용하였던 SSAO에 대해서만 적용 여부에 따른 비교를 수행한다.

Koulaxidis와 Xinogalos(2022)는 유니티로 제작한 게임의 최적화 적용본과 미적용본을 비교하면서, 초당 프레임 수(FPS), 배치(Batch) 수, 삼각형 수의 세 지표를 각각 CPU 부하와 렌더링 부하, 메모리 사용량에 대응시켜 측정하는 방법을 제시하였다. 본 연구 또한 해당 지표를 기준으로 성능을 확인한다.

각 서술의 확인 위치. **확인**은 파일에서 직접 읽은 것, **판단**은 읽은 내용에서 제가 끌어낸 해석입니다. 판단 항목은 동의하지 않으시면 빼셔도 됩니다.

|---|---|---|
| ScriptableRendererFeature 상속 | `FlashlightRendererFeature.cs` 클래스 선언 | 확인 |
| 불투명·투명 렌더링 이후 삽입 | 같은 파일 `passEvent` 기본값, `PC_Renderer.asset`의 `passEvent: 500` | 확인 |
| 깊이 버퍼 없는 텍스처로 복사 | `desc.depthBufferBits = 0;` + `AddBlitPass` | 확인 |

| 정점 버퍼 없이 3정점 절차적 드로우 | `DrawProcedural(..., MeshTopology.Triangles, 3)` | 확인 |

## 4장으로 넘긴 항목: SSAO 제거

3.9에서 빼는 대신 4장에서 측정 항목으로 다루기 위해 근거를 정리한다.

**왜 효과가 남지 않는가.** 조명 셰이더의 최종 합성은 다음과 같다.

```hlsl
static const float DARK_FACTOR = 0.02;
static const float BEAM_DIM    = 0.05;

float3 litColor = col.rgb * BEAM_DIM + flashContrib + pointContrib;
return lerp(col * DARK_FACTOR, float4(litColor, col.a), totalMask);
```

여기서 `col`이 SSAO가 적용된 화면이다. 빛이 닿지 않는 영역에서는 0.02가, 닿는 영역에서도 0.05가 곱해진 뒤 조명색이 가산되므로, SSAO가 만든 음영은 원래 세기의 2~5%로 축소된 뒤 가산된 조명에 묻힌다.

**측정 설계.** Koulaxidis와 Xinogalos(2022)의 비교 방법을 따라 SSAO 적용본과 미적용본을 각각 측정한다. SSAO는 화면 공간 패스이므로 삼각형 수와 배치 수에는 영향을 주지 않고 초당 프레임 수에만 영향을 줄 것으로 예상되며, 이는 세 지표가 각각 서로 다른 부하를 반영한다는 점을 보이는 사례가 된다. 두 버전의 화면을 나란히 제시하여 시각적 차이가 없음을 함께 보인다.

**서술 방향.** "설계 단계에서 적용하였으나 측정 결과 시각적 차이 없이 비용만 발생하여 제거하였다." 이는 설계 서술이 아니라 검증 결과이므로 4장에 속한다.

## 제출 전 확인 사항

**`PC_Renderer`에서 조명 패스가 비활성화되어 있습니다** (`m_Active: 0`). URP는 비활성 피처의 패스를 추가하지 않으므로 현재 상태로는 조명 합성이 수행되지 않습니다. 4장 성능 측정 전에 활성화가 필요합니다.

## 5장 개선 항목 후보

3.9에 쓰지 않았으나 코드에서 확인된 개선 여지.

**`Flashlight.UpdateShaderGlobals()`의 프로퍼티 전달이 문자열 키를 사용한다.** 렌더 패스 쪽은 `Shader.PropertyToID`로 캐싱되어 있으나 이쪽은 `Shader.SetGlobalFloat("_FlashlightRange", ...)` 형태로 문자열을 직접 넘기며, 한 번의 호출에 9개의 문자열 해싱이 발생한다.

**같은 함수가 프레임당 두 번 호출된다.** `Flashlight.Update()`와 `PlayerStateMachine.Update()` 양쪽에서 호출하고 있어, 위의 문자열 해싱이 프레임당 18회 발생한다.

**같은 함수 내에서 `Camera.main`을 세 번 호출한다.** 지역 변수로 한 번만 받아 재사용할 수 있다.

**사거리의 월드 단위를 뷰포트 단위로 바꾸는 배율이 상수 `0.05`로 고정되어 있다.** 카메라의 거리나 시야각이 변경되면 손전등의 사거리가 의도와 어긋난다.
