## 2. AI 활용 원칙 (학교 규정: "AI를 도구로 쓰는 건 되지만, output이 그대로 논문 결과물이 되면 안 됨")

| 구분 | 허용 여부 |
|---|---|
| 자료 조사·정리 보조, 코드 구조 파악, 목차/논리 구성 아이디어 | ✅ 허용 (도구 사용) |
| AI가 만든 문장·문단을 그대로 논문에 복붙 | ❌ 불허 |
| AI가 제안한 목차 구조를 참고해서 본인이 새로 서술 | ✅ 허용 |
| 코드 검증 결과("부록 A" 표 등)를 본인이 재확인 없이 그대로 인용 | ⚠️ 위험 — 구두시험에서 설명 못 하면 문제. 반드시 본인이 직접 코드 열어 재확인 |
| 참고문헌을 AI가 찾아준 것을 활용해 본인이 읽고 인용 | ✅ 허용 |

**실행 원칙:**
1. `구성제안.md`는 개인 설계도로만 사용, 논문 문장은 처음부터 다시 작성
2. 부록의 코드 검증 기록은 본인이 직접 코드를 열어 재확인
3. 이론적 배경(2장)은 실제 논문/자료를 본인이 찾아 읽고 인용 — AI가 대신할수록 리스크 큼
4. 최종 제출 전 AI 특유의 표현("검증이 끝났습니다" 류)이 남아있는지 자체 점검
5. AI 도구 사용 범위를 지도교수님께 미리 공유해두는 것을 권장

## 3. 구성(목차) 개요 — 참고용, 문장은 재작성 필요

**교수 코멘트 대응**: "졸작으로 원하는 건 '무슨 기능을 쓰냐'지, 콘텐츠 나열 기획서가 아님" / 5페이지·10분 발표 분량

- **1장 서론**: 연구 배경(폐쇄 공간 생존 호러 컨셉을 탐지 게이지 메카닉의 존재 이유로 서술) / 연구 목적(3계층 상태 머신, 탐지 게이지 모델, 루프 리셋 시스템) / 연구 범위·방법
- **2장 이론적 배경**: 상태 패턴과 게임 상태 머신 / 탐지 게이지형 적 AI / 데이터 구형 설계(ScriptableObject)·오브젝트 풀링
- **3장 시스템 아키텍처 및 구현** (본체, 최대 분량): 모듈 구조 → 데이터 구형 → 플레이어 상태 머신 → 탐지 게이지 AI(핵심 차별점) → 전투 시스템 → 보스 확장 → 생존·수급 → 렌더링/최적화 → 루프 진행 구조 → 튜토리얼 흐름
- **4장 결과 및 분석**: 구현 완료 체크리스트, 플레이 흐름 검증, 성능(프로파일러 수치 확보 권장), 플레이테스트
- **5장 결론 및 향후 계획**: 기여 요약, 한계점(솔직 서술), 미구현 요소는 여기로만 이관

**기획서 배치 원칙**: 콘텐츠(적 4종·스토리·맵 규칙) 나열 금지 → 1장 배경 + 5장 향후계획에만 분산. 밸런스 표는 3.2절 데이터 근거로만 인용. 기획서 구어체 원문 인용 금지.

**리스크 & 보완**:
- 상태 머신이 흔한 패턴이라는 지적 → 3계층 상속 재사용, isBlock 강제 전환 같은 고유 변형점 부각
- 탐지 게이지가 단순 누적이라는 평가 → 조건 분기 전체(장애물 감쇠, 즉각 추격, 복귀 타이머)를 다이어그램으로 증명
- 성능 주장 근거 부족 → 프로파일러/Frame Debugger 캡처 확보, 없으면 원리 서술로 격하
- 장르 표기 불일치 → "루프(Cycle) 기반 진행 구조"로 기술적 명칭 통일

## 4. 2장 참고문헌 후보 (실제 검색 결과, 직접 읽고 본인 말로 인용할 것)

**① 상태 패턴 / FSM**
- arXiv 논문 "Augmenting Game AI with Deep Reinforcement Learning" — FSM을 상태·전이·행동 그래프로 정의, 단순·저비용이라 실용적이나 대규모화 시 유지보수 복잡·적응력 부족이라는 한계 서술 (`https://arxiv.org/pdf/2606.20210`)
- De La Salle University 학사 졸업논문 사례(2010, FSM 기반 게임 AI 시각화 도구) — 학사 수준에서 FSM을 논문 주제로 다룬 선례 (`https://animorepository.dlsu.edu.ph/etd_bachelors/5394`)

**② 탐지 게이지형 스텔스 AI (핵심 차별점 절 근거)**
- Universitat de Barcelona 학사 졸업논문 "Development of a stealth game with multi-agent artificial intelligence" (2018) — 스텔스 게임 AI의 환경 인식·행동 감지·전략적 대응 구조, 순찰→조사→추격 흐름 (`https://diposit.ub.edu/items/c40de58b-3c68-4780-b52d-6b2f37f2d46e`)
- 스텔스 게임 어웨어니스 미터 개념 정리 자료 — 거리·조명·은폐에 따라 서서히 차오르다 발각 전환되는 구조, SubwayExit 게이지 모델과 업계 관행 비교에 활용 가능 (`https://wemakestuffforfun.myblog.arts.ac.uk/?p=134`)

**③ ScriptableObject / 오브젝트 풀링**
- 순수 학술논문보다 Unity 공식 문서 + Robert Nystrom, *Game Programming Patterns*(오브젝트 풀 패턴 표준 레퍼런스, 무료 온라인 공개)를 인용하는 것이 현실적. "Unity 공식 권장 패턴"이라는 위상을 문서/책으로 근거 제시.

## 5. 오브젝트 풀링 검증 결과 (2026-09, 코드 재확인)

`기능명세서.md`에 "오브젝트 풀링(MonsterManager 몬스터 풀)"이라고 적혀 있었으나, 실제 코드(`MonsterManager.cs`, `Die.cs`, `CycleManager.cs`)를 직접 열어 재확인한 결과 **명세서 서술이 실제 구현과 어긋나 있었음을 확인**:

- `MonsterManager`에 큐 기반 풀(`pool`, `Preload`, `Spawn`, `ReturnToPool`)이 존재하지만, `MonsterType` enum이 비어있고(`public enum MonsterType {}`) 어디서도 호출되지 않는 죽은 코드였음
- `Die.cs`의 `LogicUpdate()`는 "나중에 풀에 되돌리기"라는 주석만 있고 구현이 비어있었음
- 실제 사망 처리는 `Monster.enabled = false` + 레이어 변경으로 시체 상태를 유지하는 방식이고, `CycleManager.RespawnMonsters()`가 `FindObjectsByType(...Include...)`로 씬에 항상 존재하는 몬스터 오브젝트를 찾아 `CycleRespawn()`으로 재사용

**원인**: 몬스터 사망 후 시체를 파밍할 수 있어야 하는 게임플레이 요구사항 때문에, 사망 즉시 오브젝트를 비활성화·반환하는 전통적 풀링 방식과 구조적으로 충돌함.

**결정 (A안 채택)**: 큐 기반 풀 코드는 제거하고, `MonsterManager`는 "활성 몬스터 추적 + 범위 탐색(GetStunnedInRange, GetAmbushTargetInRange)" 역할로 재정의. `기능명세서.md`는 이미 이 내용으로 수정 반영함 (`11.3 MonsterManager`, `4.3 Die 상태`, `15장 설계 패턴 표`).

**논문 서술 방향** (3.4절 또는 3.9절, 본인 문장으로 재작성할 것):
> 몬스터 사망 후에도 시체를 통한 아이템 파밍을 지원해야 했기 때문에, 사망 즉시 오브젝트를 비활성화·재사용하는 전통적 오브젝트 풀링 방식 대신, 사망 상태를 유지하다가 사이클 리셋 시점에 동일 오브젝트를 재초기화하는 방식(`CycleRespawn`)을 채택했다. 이는 Instantiate/Destroy 호출 자체가 없다는 점에서 오브젝트 풀링과 동일한 성능상 이점(GC 압박 감소)을 유지하면서, 시체 파밍이라는 게임플레이 요구사항과 양립 가능한 구조다.

이 사례는 5장(한계점) 또는 3장 설계 근거 서술 어느 쪽에 넣어도 되지만, "설계 트레이드오프를 인지하고 의도적으로 다른 방식을 택했다"는 톤으로 쓰는 것이 "미구현"으로만 남기는 것보다 평가에 유리함.
