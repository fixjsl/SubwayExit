## 0. 논문 제목 확정 및 장 구성 재편 (2026-09)

**확정 제목**: 「익스트랙션 사이클 루프와 메트로베니아 공간 확장을 결합한 서바이벌 게임의 설계 및 구현」
(게임 자체의 작업명은 SubwayExit 그대로 유지, 이 문서 제목도 계속 SubwayExit으로 표기)

**제목이 지정하는 3대 축**:
1. **서바이벌 게임** — 장르 우산(생존 스탯, 실시간 위협 회피)
2. **익스트랙션 사이클 루프** — 런(run) 단위 핵심 구조(탐색→탈출→성장→구역돌파, 목숨 3개, 사망 페널티) → 기존 ⑩절 자료가 이 축의 핵심 근거
3. **메트로베니아 공간 확장** — 메타(meta) 단위 구조(열쇠/아이템 습득에 따른 맵 확장, 기지 빠른이동, 블록에이드) → 기존 ⑧절 자료가 이 축의 핵심 근거

**이전 리스크 해소**: 3절의 "장르 표기 불일치" 리스크가 이 제목 확정으로 사실상 해결됨 — 익스트랙션/메트로베니아 두 구조가 서로 다른 층위(런 vs 메타)에서 공존한다는 점을 제목 자체가 명시하므로, 더 이상 "이게 무슨 장르냐"는 질문에 방어적으로 답할 필요 없이 **제목 자체가 논지**가 됨.

**장 구성 재편 방향** (상세는 아래 3절 개정판 참고):
- **2장(이론적 배경)**: 기존에 "상태 패턴/FSM"이 2.1절 헤드라인이었으나, 제목 기준으로는 **익스트랙션 루프(2.2)**와 **메트로베니아 공간 확장(2.3)**이 먼저 오고, FSM/탐지게이지/ScriptableObject는 "지원 기술"로 뒤로 재배치
- **3장(구현)**: 익스트랙션 루프 구현(목숨 시스템·CycleManager·Skyhill 비교)과 메트로베니아 공간 확장 구현(EmergencyExit 키게이트·기지 빠른이동)이 **비중 있는 별도 절**로 승격
- **5장(한계점)**: 메트로베니아 축이 1구역만 구현되어 가시화 안 된 점을 제목의 핵심 축 중 하나가 부분 구현이라는 형태로 명확히 서술 필요 (기존보다 비중 있게 다뤄야 함 — 제목에 들어간 요소라 완전히 안 보이면 구두시험에서 반드시 질문받음)

## 2. AI 활용 원칙 (학교 규정: "AI를 도구로 쓰는 건 되지만, output이 그대로 논문 결과물이 되면 안 됨")

| 구분 | 허용 여부 |
|---|---|
| 자료 조사·정리 보조, 코드 구조 파악, 목차/논리 구성 아이디어 | ✅ 허용 (도구 사용) |
| AI가 만든 문장·문단을 그대로 논문에 복붙 | ❌ 불허 |
| AI가 제안한 목차 구조를 참고해서 본인이 새로 서술 | ✅ 허용 |
| 코드 검증 결과("부록 A" 표 등)를 본인이 재확인 없이 그대로 인용 | ⚠️ 위험 — 구두시험에서 설명 못 하면 문제. 반드시 본인이 직접 코드 열어 재확인 |
| 참고문헌을 AI가 찾아준 것을 활용해 본인이 읽고 인용 | ✅ 허용 |

**실행 원칙:**
1. `구성제안.md`는 개인 설계도로만 사용, 논문 문장은 처음부터 다시 작성
2. 부록의 코드 검증 기록은 본인이 직접 코드를 열어 재확인
3. 이론적 배경(2장)은 실제 논문/자료를 본인이 찾아 읽고 인용 — AI가 대신할수록 리스크 큼
4. 최종 제출 전 AI 특유의 표현("검증이 끝났습니다" 류)이 남아있는지 자체 점검
5. AI 도구 사용 범위를 지도교수님께 미리 공유해두는 것을 권장

## 3. 구성(목차) 개요 — 참고용, 문장은 재작성 필요 (2026-09, 제목 확정에 맞춰 개정)

**교수 코멘트 대응**: "졸작으로 원하는 건 '무슨 기능을 쓰냐'지, 콘텐츠 나열 기획서가 아님" / 5페이지·10분 발표 분량

**제목**: 「익스트랙션 사이클 루프와 메트로베니아 공간 확장을 결합한 서바이벌 게임의 설계 및 구현」

- **1장 서론**
  - 연구 배경: 지하철 폐쇄 공간 생존 컨셉 소개 → **왜 익스트랙션(런 단위 긴장)과 메트로베니아(메타 단위 성장)를 결합했는가**가 핵심 논지 — 서바이벌 장르의 반복 실패 경험(Juul)을 완충하면서도(목숨 3개) 재도전 동기(메타진행·공간 확장)를 유지하기 위한 설계 선택이라는 서술
  - 연구 목적: (1) 익스트랙션 사이클 루프 구현, (2) 메트로베니아 공간 확장 구조 설계, (3) 이를 뒷받침하는 3계층 상태 머신·탐지 게이지 AI
  - 연구 범위·방법
- **2장 이론적 배경** (제목 순서에 맞춰 재배열)
  - 2.1 서바이벌 게임 장르와 실패 설계 — 실패의 의미(Juul 일부, ⑩절). ⚠️ 생존 스탯 수치 모델(ITU 논문, ⑤절)은 사용자 기존 결정에 따라 2장이 아닌 **3.8절에서만** 인용
  - 2.2 익스트랙션 사이클 루프 — **핵심 축1**, ⑩절 전체(Cuerdo, Chang 외, Zhang, Schell) 메인 인용
  - 2.3 메트로베니아 공간 확장 — **핵심 축2**, ⑧절(Wahlberg, Oliveira) 메인 인용
  - 2.4 지원 기술 이론 — 상태 패턴/FSM(①), 탐지 게이지형 적 AI(②), 데이터 구형 설계(③) — *기존엔 2장 헤드라인이었으나 제목 기준 "구현을 뒷받침하는 배경지식"으로 위상 조정. 분량은 줄이지 않아도 되나 순서상 뒤로*
- **3장 시스템 아키텍처 및 구현** (본체, 최대 분량 — 순서 재조정)
  - 3.1 모듈 구조 개요
  - 3.2 데이터 구형(ScriptableObject)
  - 3.3 플레이어 상태 머신 + 입력 버퍼링(④, 게임 필)
  - 3.4 탐지 게이지 AI(핵심 차별점, ②)
  - 3.5 전투 시스템
  - **3.6 익스트랙션 사이클 루프 구현** — **제목 핵심 축1, 비중 확대**: CycleManager, 목숨 3개 완충 구조, 사망 페널티(아이템 손실+기지 부활), Skyhill 비교표(⑩절), 완전 게임오버 후 특성 2~3개 선택 메타진행
  - **3.7 메트로베니아 공간 확장 구현** — **제목 핵심 축2, 비중 확대**: EmergencyExit 키 게이트 구조, 기지 구역별 빠른이동 설계, 블록에이드 설계 의도(⑧절). *1구역만 구현된 현재 상태를 여기서 솔직히 명시하고, 설계 프레임워크는 확장 가능하게 만들어뒀다는 점을 강조*
  - 3.8 생존·수급 시스템(⑤)
  - 3.9 크래프팅 시스템(⑥)
  - 3.10 렌더링/최적화, 오브젝트 재사용(풀링 대체 방식 — 5절 참고)
  - 3.11 튜토리얼 흐름
- **4장 결과 및 분석**: 구현 완료 체크리스트, 익스트랙션 루프의 재도전 유도 효과(정성 서술), 메트로베니아 확장성 검증(제한적 — 1구역 기준), 성능(프로파일러 수치 확보 권장), 플레이테스트
- **5장 결론 및 향후 계획**: 기여 요약(제목의 두 축 결합이 기여점), **한계점에 "메트로베니아 공간 확장 축은 1구역만 구현되어 완전히 가시화되지 않음"을 명시적으로 서술** (제목에 들어간 요소이므로 반드시 언급 필요 — 안 쓰면 구두시험에서 지적당함), 향후 구역 확장 계획

**기획서 배치 원칙**: 콘텐츠(적 4종·스토리·맵 규칙) 나열 금지 → 1장 배경 + 5장 향후계획에만 분산. 밸런스 표는 3.2절 데이터 근거로만 인용. 기획서 구어체 원문 인용 금지.

**리스크 & 보완**:
- 상태 머신이 흔한 패턴이라는 지적 → 3계층 상속 재사용, isBlock 강제 전환 같은 고유 변형점 부각
- 탐지 게이지가 단순 누적이라는 평가 → 조건 분기 전체(장애물 감쇠, 즉각 추격, 복귀 타이머)를 다이어그램으로 증명
- 성능 주장 근거 부족 → 프로파일러/Frame Debugger 캡처 확보, 없으면 원리 서술로 격하
- ~~장르 표기 불일치~~ → **제목 확정으로 해결됨** (2026-09). "익스트랙션 사이클 루프 + 메트로베니아 공간 확장" 하이브리드 구조가 이제 논문 제목 자체
- **(신규) 메트로베니아 축 미가시화 리스크** → 제목에 명시된 두 축 중 하나(메트로베니아)가 1구역만 구현되어 실제로는 거의 안 보임. 3.7절에서 "설계 프레임워크는 구현했으나 콘텐츠(구역 수)가 부족해 체감되지 않는다"고 정직하게 쓰고, 5장에 향후계획으로 명시 — 이 리스크를 숨기지 말고 3.7/5장에서 선제적으로 다룰 것

> 실시간 전투에서는 실패 원인이 전략적 판단뿐 아니라 순간적 반응·타이밍 실행에도 있다(입력 버퍼링·콤보 캔슬 윈도우가 필요한 이유, ④절 근거). Juul(2013)의 귀인 이론으로 보면 실시간 액션에서의 죽음은 플레이어가 상황(운/타이밍) 탓으로 돌리기 쉬워 좌절감이 커질 수 있는데, 이는 완전한 permadeath보다 목숨 3개의 완충 구조(Cuerdo, 2022의 체크포인트+게임오버 혼합형)가 실시간 액션 장르에 더 적합한 이유가 된다. 완전 게임오버 이후에는 Skyhill류 로그라이트의 메타진행 방식을 차용해, 해금된 특성 중 일부를 선택해 다음 판에 적용하도록 설계했다.

## 5. 오브젝트 풀링 검증 결과 (2026-09, 코드 재확인)

`기능명세서.md`에 "오브젝트 풀링(MonsterManager 몬스터 풀)"이라고 적혀 있었으나, 실제 코드(`MonsterManager.cs`, `Die.cs`, `CycleManager.cs`)를 직접 열어 재확인한 결과 **명세서 서술이 실제 구현과 어긋나 있었음을 확인**:

- `MonsterManager`에 큐 기반 풀(`pool`, `Preload`, `Spawn`, `ReturnToPool`)이 존재하지만, `MonsterType` enum이 비어있고(`public enum MonsterType {}`) 어디서도 호출되지 않는 죽은 코드였음
- `Die.cs`의 `LogicUpdate()`는 "나중에 풀에 되돌리기"라는 주석만 있고 구현이 비어있었음
- 실제 사망 처리는 `Monster.enabled = false` + 레이어 변경으로 시체 상태를 유지하는 방식이고, `CycleManager.RespawnMonsters()`가 `FindObjectsByType(...Include...)`로 씬에 항상 존재하는 몬스터 오브젝트를 찾아 `CycleRespawn()`으로 재사용

**원인**: 몬스터 사망 후 시체를 파밍할 수 있어야 하는 게임플레이 요구사항 때문에, 사망 즉시 오브젝트를 비활성화·반환하는 전통적 풀링 방식과 구조적으로 충돌함.

**결정 (A안 채택)**: 큐 기반 풀 코드는 제거하고, `MonsterManager`는 "활성 몬스터 추적 + 범위 탐색(GetStunnedInRange, GetAmbushTargetInRange)" 역할로 재정의. `기능명세서.md`는 이미 이 내용으로 수정 반영함 (`11.3 MonsterManager`, `4.3 Die 상태`, `15장 설계 패턴 표`).

**논문 서술 방향** (신 목차 3.6절[익스트랙션 루프/CycleManager] 또는 3.10절[렌더링·최적화], 본인 문장으로 재작성할 것):
> 몬스터 사망 후에도 시체를 통한 아이템 파밍을 지원해야 했기 때문에, 사망 즉시 오브젝트를 비활성화·재사용하는 전통적 오브젝트 풀링 방식 대신, 사망 상태를 유지하다가 사이클 리셋 시점에 동일 오브젝트를 재초기화하는 방식(`CycleRespawn`)을 채택했다. 이는 Instantiate/Destroy 호출 자체가 없다는 점에서 오브젝트 풀링과 동일한 성능상 이점(GC 압박 감소)을 유지하면서, 시체 파밍이라는 게임플레이 요구사항과 양립 가능한 구조다.

이 사례는 5장(한계점) 또는 3장 설계 근거 서술 어느 쪽에 넣어도 되지만, "설계 트레이드오프를 인지하고 의도적으로 다른 방식을 택했다"는 톤으로 쓰는 것이 "미구현"으로만 남기는 것보다 평가에 유리함.
