# 생존 메카닉 인용 위치 설정 분석 (ITU 비선형 논문 vs 고정수치 구현)

> 질문: 논문메모(⑤번)에서 ITU 논문을 "비선형 함수 모델"로 서술했는데, 내 게임은 고정수치 감소인데 이 부분을 써도 되는가?
> 결론: **써도 된다. 단, "모델을 구현했다"가 아니라 "참조 프레임워크 → 선형 하위 모델 단순화 채택"으로 서술해야 한다.**
> **위치 확정 (2026-09 사용자 지시)**: 제2장(관련연구) 배경이 아닌, **제3장 시스템 구현의 3.7절(생존·수급)에서 직접 인용·기술한다**.

---

## 1. 사실관계 확인 (논문 vs 실제 코드)

### 1-1. 논문이 실제로 주장하는 것
Kutay Tinç, Reyhan Eren, "Using Mathematical Models in Game Design: A Survival Mechanics Case", *Springer Series in Design and Innovation*, 2021.

초록 원문(ITU 연구정보시스템에서 확인):

> "…a mathematical model framework for survival mechanics that will consist of **various nonlinear functions that affect each other**, and in exchange affected by different consumables or states…"

- 갈증·스태미나·배고픔·수면을 **서로 영향을 주고받는 비선형 함수 네트워크**로 모델링하는 프레임워크 제안 논문.
- "비선형"이 핵심 단어인 것은 맞음.
- 출처: https://research.itu.edu.tr/en/publications/using-mathematical-models-in-game-design-a-survival-mechanics-cas/

### 1-2. 내 게임의 실제 구현 (코드 근거)

**`Assets/Script/State/PlayerState/PassiveState/HungerThirst.cs` — 배고픔/갈증 감소**
- `GameManager.ChangeTime`(게임 시간 1분 틱) 이벤트 구독
- 매 분마다 `hungerAccum += hungerDecreasePerMinute`(기본 0.1), `thirstAccum += waterDecreasePerMinute`(기본 0.3) 누적
- 누적값이 정수 1 이상일 때만 상태 값(`Hungry`/`Water`)에서 차감
- → **정확히 "고정 비율(선형) 감소"**. 다른 스탯에 따라 기울기가 변하지 않음

**`Assets/Script/Status/PlayerStatus.cs` — 스테미나**
- 행동당 고정 비용: `attackStamina` / `guardStamina` / `parryStamina` / `DodgeCost`(무기별 ScriptableObject 값)
- 회복은 `staminaRecoverey * Time.deltaTime` 상수율
- → 이것도 **선형**

**다만 핵심 예외가 하나 있다:**

```csharp
// PlayerStatus.cs — Water setter
if (water <= 30)
    curMaxStamina = (int)(MaxStamina * 0.4f);   // 갈증이 낮으면 스테미나 상한이 60% 감소
else
    curMaxStamina = MaxStamina;
```

`Water ≤ 30`이면 `curMaxStamina`가 `MaxStamina × 0.4`로 떨어짐. 이건 바로 논문이 말하는 **"스탯 A의 변화가 스탯 B에 영향을 준다"는 상호의존(interdependence) 그 자체**.

### 비교 표

| 구분 | 논문 모델 | 내 구현 |
|---|---|---|
| 감소 곡선 | 연속 비선형 함수 | **분당 고정 감소(선형)** |
| 스탯 간 결합 | 연속적 상호의존 네트워크 | **이산 커플링 1개**(갈증≤30 → 스테미나 상한 40%) + 행동 기반 스테미나 비용 |

**정리: "완전 독립적인 고정수치 감소"가 아니라, "선형 감소 + 상태 기반 이산 커플링 1종".**
이 구분이 인용 성패를 가르는 포인트.

## 2. 써도 되는 이유와 조건 (4가지)

핵심 원칙: **"그 논문을 구현했다"고 쓰면 안 되고, "그 논문이 제시한 관점(prior art)을 참고해 단순화·선형화된 하위 모델을 설계했다"고 쓴다.**

졸업논문에서 공개 문헌의 모델을 프로젝트 목적에 맞게 단순화하는 것은 정상적인 설계 판단이다. 반대로 원문 모델과 구현이 안 맞는데도 "우리는 [X]의 모델을 적용했다"고 쓰면, 심사 시 "어디가 비선형이고 어디가 서로 영향을 주는가"라는 질문에 답할 수 없게 된다.

### 조건 1 — 서술 방향: '실현'이 아닌 '참조 프레임워크 → 단순화 채택'
"[X]은 생존 스탯을 상호의존적 비선형 함수로 모델링하는 프레임워크를 제안한다. SubwayExit는 이 관점에서 배고픔·갈증을 분당 감소율(0.1/0.3)이라는 선형 파라미터로 표현하되, 아래 이유로 단순화했다."
이렇게 쓰면 논문의 "비선형"과 내 구현의 "고정수치"가 충돌하지 않음.

### 조건 2 — 왜 단순화했는지 설계 근거를 한 문단으로 정당화 (모두 사실에 기반)
- **범위**: 핵심 루프는 탐지 게이지 스테ルス + 익스트랙션이고, 생존은 배경적 압박감(background tension)이지 독립 시스템이 아님.
- **예측 가능성**: 고정 감소율은 플레이어가 현재 인벥토리로 "몇 시간/几日 버틸 수 있는지" 계산 가능하게 만들어, 1판 단위(실시간 1시간 = 게임 1일) 익스트랙션 루프의 자원 의사결정(먹을 거 들고 갈지, 물 우선 마실지)에 직접 연결됨.
- **튜닝 비용**: 비선형 상호의존은 변수 간 결합으로 튜닝 축이 급격히 늘어남. 졸업논문 범위에서 스테ルス 핵심 메카닉 완성도에 우선순위 둔 것.

### 조건 3 — 이미 존재하는 커플링을 "단순화해서 채택한 부분"으로 꺼내기 (가장 강한 카드)
`Water ≤ 30 → curMaxStamina × 0.4`는 논문 핵심 주장(스탯은 독립적으로 줄지 않는다)을 **이산/단계 형태로 흡수한 구현**.
서술 예: "본 연구는 [X]의 상호의존 원칙 중 '갈증이 스테미나에 영향을 준다'는 경로를 상한값 단계 감소로 단순화해 반영했다."
→ 단순히 "참고만 했다"가 아니라 **"원칙을 일부 구현했다"** 가 됨.

### 조건 4 — 확장 지점을 한계점/향후연구(5장)에 명시
`PlayerStatus.cs`에 이미 기본값 보존 필드가 예약되어 있음:
- `baseHungerDecreasePerMinute` / `baseWaterDecreasePerMinute` / `baseStaminaRecovery`
- `PlayerStateMachine.cs`(사이클 리셋 시점)가 이들을 저장/복원하는 구조

즉 "수치 수정자(modifier)"가 들어갈 자리가 아키텍처적으로 이미 만들어져 있음 → 향후연구에 "특성·아이템 기반 감소율 변형(비선형화 방향)을 확장 가능"이라고 한 줄 쓰면, 단순화를 '미완'이 아니라 **'확장 가능한 설계 결정'** 으로 보여줄 수 있음.

## 3. 쓸 수 있는 방식 (권장순)

### 방법 A — "참조 프레임워크 → 선형 하위 모델 채택" 서술 (★강력 추천)
- **제2장(관련연구)에는 올리지 않고**, 제3장 시스템 구현의 3.7절(생존·수급)에서 "선행 연구 [X]는 생존 스탯을 상호의존적 비선형 함수로 모델링한다 → 본 프로젝트는 이 관점을 받아 분당 감소율이라는 선형 파라미터 + 갈증→스태미나 상한 커플링으로 단순화했다"고 **직접 인용·기술**한다
- 장점: 가장 정직하면서 학술 근거도 유지. 심사 질문("왜 비선형을 안 썼나?")에 조건 2의 근거로 답할 수 있고, 커플링 덕분에 "아예 무시했다"가 아님

### 방법 B — 배경 문헌으로만 격하
- 제2장 배경에 두지 않고 [X]를 "생존 스탯 모델링이 학문적으로 다루어지고 있음을 보여주는 참고 문헌"으로만 쓰고, 3.7절 설계 근거에는 GameDesignSkills(실무) + 자기 설계 설명을 둔다
- 장점: 가장 안전(비교 대상 자체가 사라짐). 단점: 3.7절의 학술적 무게가 약해지고, 메모에서 정한 "수치 설계의 1차 학술 근거" 역할 상실

### 방법 C — 구현을 먼저 비선형 쪽으로 약간 확장한 뒤 인용
- 예: 갈증 구간별 스테미나 회복율 변화, 또는 특성 기반 감소율 배율을 modifier로 하나 더 넣으면 [X]를 "직접적 설계 근거"로 쓰는 것이 성립
- 단점: 구현 작업량 발생. 시간 여유 있을 때만 A+C 하이브리드 권장(현재 `base*` 필드 구조 덕분에 추가 비용이 작음)

**권장: A 기본 + 가능하면 C의 작은 한 가지만 더.** B는 "근거가 아예 없으니 빼자"는 경우 외에는 불필요하게 보수적.

### 방법 D — 완전 제외 (인용 0회, 사용자 제안 2026-09)
- 3.7절에서 ITU 논문을 전혀 인용하지 않고, 고정 감소율 채택을 **자기 설계 판단**(예측 가능성 → 익스트랙션 판 자원 계산)으로만 서술. Game Design Skills(비학술 보조)도 같이 제거
- 장점: 구두시험 공격면 최소화("왜 비선형을 안 썼나" 질문 자체 소멸), 원문 독해 부담 0, 작성 분량 최소
- 단점: ① 제3장 다른 절들(버퍼입력·크래프팅·실패 설계는 전부 참고문헌 보유)과 달리 **참고문헌 제로 구간**이 생겨 인용 균형 깨짐 ② "의도적으로 단순화했다"는 설계 판단 서술에 기준점이 없어 평면적 설명으로 약화(진행메모 5절의 풀링 사례 원칙과 정반대 톤) ③ `Water≤30→×0.4` 커플링을 "상호의존 원리를 이산 형태로 흡수했다"고 격상시키는 카드 소멸
- **적용 기준(해당 시 D로 하강)**: (a) 구두시험 대비 시간이 부족하고 ITU 논문 원문을 직접 읽기 전 상태 — 읽지 않은 인용은 오히려 리스크 / (b) 지도교수의 참고문헌 최소화 성향 확인 / (c) 3.7절이 최종적으로 매우 짧은 구간(약 1/2페이지 이하)으로 압축될 경우
- **결론: 기본 = A 유지 + 원문을 직접 읽되 얕게 인용. "안 읽으면 안 쓴다"가 안전장치.**

## 4. 3.7절에 바로 쓸 수 있는 문장 초안 (수정해서 사용)

> 생존 게임에서 갈증·배고픔·스태미나 등은 서로 독립적으로 감소하는 것이 아니라, 상태 간 상호의존을 통해 플레이어에게 복합적 압박을 주는 것으로 모델링될 수 있다[Tinç & Eren]. 본 프로젝트는 이 관점을 참고하되, 핵심 루프가 스테일러스 탈출에 있다는 점을 고려해 감소 곡선을 분당 고정 감소율(배고픔 0.1/분, 갈증 0.3/분)으로 단순화하였다. 이는 플레이어가 현재 보유 자원으로 유지 가능한 시간을 직접 계산할 수 있게 하여, 익스트랙션 판 단위 자원 의사결정과 연결된다. 한편 스탯 간 결합이라는 원론적 원칙은 이산 형태로 반영하였는데, 갈증이 임계값(30) 이하로 떨어지면 최대 스테미나가 40%로 감소하여 이동·공격 지속력이 직접 저하된다. 향후에는 기본값 보존 필드(`base*`)를 기반으로 특성·아이템에 따른 감소율 변형을 확장할 수 있다.
