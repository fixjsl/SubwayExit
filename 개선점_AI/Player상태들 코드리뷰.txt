PlayerState 전체(ActiveState 11종 + PassiveState 3종) 리뷰를 완료했습니다. 종합 평가와 개선안을 정리합니다.

## 📋 종합 평가

전체 구조(State → PlayerState → Active/Passive 분기, StateMachine으로 전환)는 깔끔하고 확장 가능한 좋은 설계입니다. 다만 **파일 간 중복 로직**, **상태 클래스에不属于(不属于→不属于) 게임 플로우 로직 혼입**, 그리고 몇 가지 **실제 버그 의심 지점**이 있습니다.

## 🔴 우선 수정 권장 (버그 의심)

### 1. `Execution.cs` — 애니메이션 즉시 덮어쓰김
```csharp
player.animator.CrossFade(player.excution, 0.15f);   // layer 0
player.animator.CrossFade(player.idle, 0.15f, 0);    // layer 0 ← 바로 다음 줄에서 덮어씀
```
두 번째 CrossFade가 같은 레이어(0)의 `excution`을 즉시 덮어써 처형 애니메이션이 거의 안 나올 수 있습니다. 의도가 "처형 후 idle 복귀"라면 애니메이션 이벤트/타이밍으로 전환하는 것이 맞고, 오타(`excution`)도 함께 수정할 것을 권장합니다.

### 2. `Move.cs` / `Crunch.cs` — 잔존 디버그 로그
```csharp
Debug.Log("Turn Animation Finished");
```
양쪽 `OnTurnAnimationFinished()`에 남아 있습니다.

### 3. `NoiseABright.cs` — 인코딩 깨짐 + 미사용 필드
- `[Header("소음 설정")]`이 `???? ??ġ`로 깨져 있음 (파일 인코딩 문제, UTF-8 BOM으로 저장 필요)
- `public Light light;`를 생성자에서 할당하지만 **전체 코드에서 사용되지 않음** → 제거 또는 사용

### 4. `HungerThirst.cs` — base.Enter() 미호출
```csharp
public override void Enter() { subscribeCoroutine = player.StartCoroutine(WaitAndSubscribe()); }
// base.Enter() 호출 없음 → PassiveRoutine(OnTick 루프)이 절대 실행되지 않음
```
현재 `OnTick()`이 비어 있어 문제가 없지만, 나중에 OnTick에 로직을 넣으면 **정적(still)으로 동작하지 않습니다.** Enter/Exit에서 `base.Enter()/base.Exit()` 호출을 명시하거나, 코루틴 기반 tick이 불필요한 이 클래스는 PassiveState 상속 자체를 재고해야 합니다.

## 🟡 설계 개선 권장

### 5. 스태미나 로직 3중 중복 (Idle / Move / Crunch)
```csharp
// 세 파일 모두에 동일한 패턴 존재
if (!player.isSprint || player.isTired)
    player.status.Stamina += player.status.staminaRecoverey * Time.deltaTime;
else
    player.status.Stamina -= player.status.SprintCost * Time.deltaTime;
```
→ `PlayerState.LogicUpdate()` 베이스 또는 **전용 PassiveState(StaminaManager)**로 통합. 상태 클래스는 "스탯 계산"이 아니라自己的行为(자기 행동)만 가지는 것이 원칙입니다.

### 6. Move / Crunch 코드 중복 (회전 버퍼, 스프린트 판정, 속도 적용)
두 클래스가 거의 동일하게 생김 → 공통 베이스 `MovingState : PlayerState` 추출:
```csharp
public abstract class MovingState : PlayerState {
    protected float moveBuffer;
    protected bool canSprint;
    // 회전 전환 로직, 스태미나 계산, linearVelocity 적용을 가상 메서드로 제공
}
```

### 7. `Die.cs` — 리스폰/게임 플로우 로직 혼입
```csharp
player.status.Chance--;
CycleManager.Instance.ExecuteCycleReset();
GameManager.Instance.GameOver();
```
데스 상태가 **게임 진행 규칙(기회 수, 사이클 리셋, 게임오버)**을 직접 알고 있음 → `RespawnManager` 또는 GameManager로 이동. Die는 "죽은 동안 입력 무시 + 애니메이션 재생"만 담당.

### 8. `Interect.cs` — 상태(State)가 아님
Enter()에서 상호작용을 즉시 실행하고 끝나는 **명령(Command)** 성격의 코드인데 State 패턴으로 감싸고 있습니다. 또한:
- 클래스명/메서드명 오타: `Interect` → `Interact`, `Oninterect` → `OnInteract`
- 미사용 필드: `private Object interectObject;`
- `nearbyInteractable == null`일 때 상태가 Interect에 머무르는데 복귀 전환 로직이 불명확

→ 입력 핸들러에서 직접 호출하는 액션 메서드로 변경, 또는 최소한 이름 수정 + 미사용 필드 제거.

### 9. 애니메이션 마법 숫자 (마법 넘버)
- 레이어 번호 `0`, `1`이 코드 전체에 하드코딩 → `const int UPPER_LAYER = 1;` 등 상수화
- `shortNameHash != player.tired` 비교 패턴 반복 → Animator 파라미터(Bool/Trigger) + 상태머신 내부 전환으로 옮기면 코드량이 크게 줄어듦 (장기 개선)

### 10. `Hit.cs` — HandleDamage의 사후 처리 부재
```csharp
public override void HandleDamage(float Damage) {
    player.status.Hp -= Damage;   // Hp <= 0 시 Die 전환은 누가 하는지 불명확
}
```
사망 판정 지점을 한 곳에 모으는 것이 좋습니다.

## ✅ 개선 실행 계획 (우선순위 순)

| 단계 | 내용 | 파일 |
|------|------|------|
| 1 | 버그 수정: Execution 이중 CrossFade, Debug.Log 제거, 인코딩 복구, 미사용 필드/변수 정리 | Execution, Move, Crunch, NoiseABright, Interect |
| 2 | PassiveState Enter/Exit base 호출 일관성 확보 | HungerThirst |
| 3 | 스태미나 계산 통합 (PassiveState 또는 베이스 메서드) | Idle, Move, Crunch (+신규) |
| 4 | MovingState 베이스 추출으로 Move/Crunch 중복 제거 | Move, Crunch |
| 5 | Die의 게임 플로우 로직을 GameManager/RespawnManager로 이동 | Die, GameManager |
| 6 | 네이밍 컨벤션 정리 (Interact, execution 등) + 레이어 상수화 | 다수 |

위 계획대로 단계 1~2(버그 수정)부터 진행할까요, 아니면 전체 리팩토링(3~6 포함)까지 한 번에 진행할까요? 원하시는 범위를 알려주시면 ACT MODE에서 바로 작업하겠습니다.
