script 폴더의 플레이어 상태머신 관련 파일들을 읽었습니다. 아래는 평가입니다.

## 대상 파일
- `Assets/Script/State/State.cs` (기본 State)
- `Assets/Script/State/PlayerState/PlayerState.cs`
- `Assets/Script/State/PlayerState/PlayerStateMachine.cs`
- `ActiveState`: Attack, Idle, Move 등

## 전체 구조 평가

장점:
1. **상태 패턴 + 캐시 풀** 구조가 적절합니다. `Assembly.GetExecutingAssembly().GetTypes()`로 PlayerState 하위 클래스를 리플렉션으로 찾아 `Statecaches`에 인스턴스를 미리 만들어 재사용하는 방식은 상태 전환 시 GC 배생을 줄여주는 좋은 설계입니다.
2. **Active/Passive 상태 분리**가 명확합니다. `AddpassiveStat<T>()`, `RemovepassiveStat<T>()`로 HungerThirst, NoiseABright 같은 지속 상태를 별도 관리하고 있습니다.
3. **입력 버퍼링 시스템**이 잘 되어 있습니다. `SetBuffer`, `ConsumeBuffer`, `buffertime`(0.2초) 조합으로 공격/도주/상호작용 입력을 버퍼링해 반응성을 높이고 있고, 공격 캔슬/콤보 윈도우(`isInCancelWindow`, `isInComboWindow`)까지 세분화되어 있습니다.
4. 애니메이션 이벤트 기반 상태 전환(`OnAnimationFinishedAt(int attackIndex)`)으로 콤보 인덱스를 매칭하는 방식이 깔끔합니다.

## 발견한 문제점 (우선순위순)

### 🔴 1. `canChanged` 초기값 리셋 누락 — 가장 큰 버그 위험
`State.canChanged`는 기본값 `true`이고, 상태가 **중단되어 Exit**될 때 리셋되지 않습니다.

- `Attack.Enter()`에서 `canChanged = false`, 애니메이션 종료 시에만 `true`로 복귀합니다.
- 그런데 공격 도중에 Dodge/Parry 캔슬 윈도우로 다른 상태로 가면 `OnAnimationFinishedAt`이 안 불려 **`canChanged`가 영구적으로 `false`**가 됩니다 → 이후 `CheckStateChange()`에서 상태 전환 자체가 전부 막히는 버그가 발생합니다.

**권장 수정**: `PlayerStateMachine.ChangeState<T>()`에서 새 상태로 갈 때 `ActiveState.EnableChange()`(또는 `canChanged = true`)를 명시적으로 호출하거나, 각 상태의 `Exit()`에서 초기화하는 것이 안전합니다.

### 🔴 2. `Attack.CanEnter()`의 null 참조 위험
```csharp
if (player.currentWeapon == null) return false;
return Time.time - lastCombo3FinishTime >= player.currentWeapon.status.attackSpeed;
```
`currentWeapon`이 null이면 앞선 guard에서 막아주지만, `attackSpeed`가 0 이하인 무기나 데이터 미설정 상태면 쿨다운 로직이 깨집니다. 또한 `lastCombo3FinishTime = float.MinValue` 초기값이라 첫 공격은 항상 통과하는 점은 의도된 것으로 보입니다만, `CanEnter()`는 **버퍼 입력 시점**과 **실제 진입 시점**이 달라질 수 있어 타이밍 기반 조건을 여기서 검사하는 것은 주의가 필요합니다.

### 🟡 3. `Move` 상태의 회전 로직 문제
```csharp
float targetY = (movebuffer > 0) ? 90f : -90f;
player.Rb.rotation = Quaternion.Euler(0, targetY, 0);
```
- 이동 방향 반전 시 **즉시 90도 스냅 회전**을 `Rb.rotation`에 직접 적용합니다. `OnAnimatorMove()`에서 `animator.deltaRotation`으로 회전을 처리하고 있는데, 이 두 방식이 충돌할 수 있습니다(애니메이션이 회전을 담당하는 중인데 코드에서도 강제로 rotation을 덮어씀).
- `movebuffer`가 0일 때(직진)에도 방향 반전 감지가 되는지 확인 필요. 현재는 `MoveInput != movebuffer` 조건이라 직진→좌/우 전환은 잡히지만, 좌↔우 직접 전환 시 애니메이션이 제대로 재생되는지 검증 권장.

### 🟡 4. `Idle.LogicUpdate()`의 스태미나 회복
```csharp
if(player.status.Stamina != player.status.MaxStamina)
    player.status.Stamina += player.status.staminaRecoverey * Time.deltaTime;
```
- 부동소수점 비교로 `!=`를 쓰지만 기능상 문제는 없습니다. 다만 **스태미나 회복 로직이 Idle 상태에만** 있고, Move 상태에서는 스프린트 중/후에만 처리됩니다. 다른 상태(Attack, Guard 등)에서는 스태미나가 전혀 회복되지 않는 것이 의도된 것인지 확인 필요.

### 🟡 5. `PlayerStateMachine`의 책임 과다
하나의 클래스에 다음이 모두 모여 있습니다:
- 입력 처리(InputSystem_Actions)
- 상태 머신 관리
- 인벤토리/무기/등불 관리
- 상호작용 대상 탐색(`nearbyInteractables`)
- 디버그 로직

SRP(단일 책임 원칙) 관점에서 `InputHandler`, `InteractionManager` 등을 분리하면 가독성과 유지보수성이 크게 좋아집니다. 특히 `stateInit()`이 60줄 넘게 되는 점은 주의가 필요합니다.

### 🟢 6. 사소한 문제들
- `State.cs`: `isBlock` 필드가 선언만 되고 어디서도 사용되지 않음 (dead code)
- `PlayerState.OnAnimationFinished()`: 기본 구현에서 `Debug.Log`가 매번 출력되어 로그가 오염됨 → `#if UNITY_EDITOR` 또는 Debug 레벨로 감싸는 것 권장
- `Attack.cs`: `ComboIndex > 2` 체크 후 return하는데, 그 전에 이미 `ComboIndex++`이 되어 있음. 로직상 문제는 없지만 가독성 개선 가능
- `Move.cs`: `curUpperAni` 필드가 선언되어 있지만 실제로는 매 프레임 재조회하므로 필드 자체가 불필요할 수 있음
- 네이밍: `Interect`(typo, Interact), `parrysucess`(success), `incrunch/outcrunch`(crouch) 등 철자 오류 다수

## 종합 의견

전체적으로 **상태 패턴 적용은 잘 되어 있고, 입력 버퍼링/콤보 시스템까지 세분화되어 있어 게임플레이 반응성 측면에서 좋은 설계**입니다. 다만:
1. **`canChanged` 리셋 문제**는 실제 플레이 중 상태 머신이 "凍結"되는 치명적 버그로 이어질 수 있으므로 우선 수정 권장
2. `PlayerStateMachine`의 책임 분리는 장기적으로 꼭 필요한 리팩토링

이 정도 규모(10개 내외의 ActiveState)라면 현재 구조가 충분히 작동하지만, 상태가 더 늘어난다면 **상태 간 전이를 선언적으로 관리하는 2D 전이 테이블** 또는 **히에라키컬 상태 머신(HSM)** 도입도 고려해볼 만합니다.
